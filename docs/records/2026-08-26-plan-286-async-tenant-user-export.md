# Async full-result tenant-user export via worker jobs (Lane #286) — Implementation Plan

> **For agentic workers:** execute task-by-task, one commit per task, push after every commit. Steps use checkbox (`- [ ]`) syntax. Every task is TDD: the named spec goes RED first, then GREEN.

**Goal:** Close #286. Today the only shipped tenant-member export is `GET /staff/tenants/{tenantId}/users/export` (`ExportTenantUsersAsStaff.Handle`, `apps/api/Modules/Users/Handlers/Staff/ExportTenantUsersAsStaff.cs`): synchronous CSV streamed from the request, capped at `TENANT_USER_EXPORT_MAX_ROWS` (default 10000, `.env.example:118`) with a 400 "narrow your filters" when exceeded. The product decision recorded in #286 is explicit: the final behavior exports the **entire filtered result set**, runs **asynchronously as a worker job**, and gives the user a clear **export-job UX** instead of holding the request open. The blocker named in the issue ("future worker service") no longer exists: Epic A landed the durable job engine (`apps/api/Infrastructure/Jobs/` — `IJobEnqueuer`, `JobDefinition<T>`, `IJobHandler`, `JobQueueProcessor`, DLQ, Quartz scheduler). An A5 PLAN (not yet implemented) was opened in parallel at `f89bc1cd1` (`docs/records/2026-08-26-plan-a5-staff-jobs-dashboard.md`); it proposes a staff-only read/mutation surface over the existing jobs infrastructure but has not landed on develop — `git grep` for `StaffJobs\|/staff/jobs` returns zero hits, and the only staff-jobs surface today is the K-1 dead-letter group at `/staff/dead-letter` (`JobDeadLetterEndpointsForStaff`). This plan therefore assumes no staff jobs dashboard and stands on its own: status and download link are read off the request rows we own, surfaced through the new endpoints in Task 6, and shown in the new export drawer in Task 8. If/when A5 ships, a `follow-up lv2` issue can wire a cross-link from the A5 list to the new export-job row; the data model here stays independent.

**Architecture:** A new domain slice lives entirely in `apps/api/Modules/Users/` (the export is about tenant users; the Jobs module keeps hosting only cross-domain engine concerns, mirroring how `PublishingJobs` lives in `Modules/Publishing/Jobs` and `AuthEmailJobs` in `Modules/Auth/Jobs`). Four moving parts:

1. **Request entity.** `UserExportRequest` (`[Table("user_export_requests")]`, `BaseAttributes` + `ITenantEntity`): one row per requested export. Columns: `tenant_id`, `requested_by_user_id`, `status` (smallint: `Pending=10, Running=20, Completed=30, Failed=40`), `format` (smallint: `Csv=10, Json=20`), `filters_json` (jsonb — the **normalized** filter snapshot, see D4), `row_count` (int, null until completed), `error` (text, null unless failed — sanitised, plain words, owner rule 2026-08-22), `file_path` (text, null until completed — storage-relative), `file_expires_at` (timestamptz, null until completed), plus the `BaseAttributes` audit columns. Indexes: `ix_user_export_requests_tenant_created` on (`tenant_id`, `created_at desc`). Expand-only migration, applied by the one-shot `migrate` service.
2. **Job.** Definition catalog `Modules/Users/Jobs/TenantUserExportJobs.cs`: `JobDefinition<ExportTenantUsersPayload>` with `JobType = "users.export-tenant.v1"` (F14 versioned key), `Priority = 0` (bulk work, §4.1), `MaxAttempts = 3` (see D2 rationale), `Validate` rejecting empty `RequestId`/`TenantId` and unknown formats. Payload carries IDs only (`{"requestId":"…","tenantId":"…"}`) — the worker reloads the request row fresh at run time, exactly the staleness-proof pattern of `PasswordResetEmailPayload` (`Modules/Auth/Jobs/AuthEmailJobs.cs`). Handler `Modules/Users/Jobs/ExportTenantUsersJobHandler.cs`.
3. **Delivery.** The finished artifact is downloaded ONLY through the new staff-gated handler `ExportArtifactForStaff` (Task 7). The r2 assumption that a `private/` prefix alone hides it is FALSE — verified against `origin/develop` (r3 evidence: `.dump/citations-r3.md`): `Program.cs` mounts the tree's ONLY `UseStaticFiles` with `FileProvider = new PhysicalFileProvider(fileStorage.RootPath)` and `RequestPath = "/files"` (`Program.cs:258-269`), which serves the ENTIRE storage root recursively, and `LocalDiskFileStorage.SaveAsync` composes `Path.Combine(_rootPath, relativePath)` via `ResolveFullPath` (`LocalDiskFileStorage.cs:51,107`) — so an export blob written under `private/user-exports/…` would land INSIDE the anonymously-served root and be readable at `GET /files/private/user-exports/…` with no session. The plan therefore scopes the mount to the upload tier FIRST (r5-corrected formula): `FileProvider = new PhysicalFileProvider(Path.Combine(fileStorage.RootPath, "uploads"))` **and** `RequestPath = "/files/uploads"` in Program.cs. The pairing is load-bearing: StaticFiles strips `RequestPath` off the request BEFORE resolving the remainder under the `FileProvider`, so this pair maps `/files/uploads/YYYY/MM/<file>` → `<Root>/uploads/YYYY/MM/<file>` — exactly where every existing producer writes (each serves `$"/files/{relativePath}"` with `relativePath` already beginning `uploads/`: `CreateStaffUpload.cs:146`, `AttachPostImageForTenant.cs:250`; algebra + evidence `.dump/citations-r5.md` C0/C1bis/C3). The r4 draft kept `RequestPath = "/files"` under the scoped root, which double-counts `uploads/` (`/files/uploads/…` → `<Root>/uploads/uploads/…`, nonexistent) and would 404 the upload tier's own control in the otherwise-fixed state. Export artifacts then live under `private/user-exports/…` — physically outside the `uploads/` subtree this mount resolves — and are read only through the gated handler. `IFileStorage.SaveAsync` gains an explicit trailing `folder` parameter — NO default (r4 decision, see D7): a default is precisely what makes a semantic drift invisible at existing call sites, which compile and pass while the bytes move. Both existing production callers (the tree's ONLY non-spec `SaveAsync` callers, `CreateStaffUpload.cs` / `AttachPostImageForTenant.cs`) pass `"uploads"` explicitly at the call site, and the no-drift claim is ANCHORED by per-tier path-pin specs (Task 4), not affirmed; the export worker passes `private/user-exports`, yielding server-generated UUID v7 names under `<folder>/yyyy/MM/<uuidv7>.<ext>` with the same `^[a-z0-9]{1,8}$` extension validation and traversal-proof resolution. Two distinct properties, never conflated again: (1) `ServedUploadPath.ExtractOrNull` only recognizes image extensions under `/files/uploads/`, so export blobs stay invisible to upload reference ACCOUNTING; (2) serving isolation comes from the scoped mount plus the gated route, proven by the Task 7 adversarial spec, not by naming convention.
4. **UX.** The staff tenant-users page grows an export drawer (mirroring `routes/authed/staff/audit-logs/_audit-log-export-drawer.tsx` in placement and interaction): pick CSV or JSON, capture the active `q`/`status`/`level` URL state, POST the job, then poll. **Selected-rows export stays exactly as it is** (≤100 IDs, instant, synchronous) — the async path exists precisely for the case the sync path refuses: whole-filtered-result exports.

## Design decisions (with alternatives)

**D1 — One job type, IDs-only payload.** Alternatives: (a) embedding filters in the payload was rejected: the request row is the single source of truth for status/progress/artifact, and a payload copy invites drift; (b) a generic "query export" engine was rejected as speculative: one concrete job type ships the behavior the issue asks for.

**D2 — MaxAttempts 3, priority 0.** An export is user-initiated: three attempts span roughly the period during which the requester still cares, versus the ~2h-of-retries default of 10 (`JobBackoff.DefaultMaxAttempts`); each retry re-runs a heavy scan, so ten attempts would hammer the database for a request nobody is waiting on anymore. The failed end state is always visible on the request row (D6), never only in the DLQ.

**D3 — Idempotency and dedup.** At-least-once execution is the engine contract. The handler guards re-runs: a request already `Completed` yields `JobOutcome.Cancelled("already-completed")` (never rewrites the file), a request already `Failed` stays failed. Enqueue passes `EnqueueOptions.IdempotencyKey = $"users-export:{tenantId}:{format}:{sha256(canonical-filters)[..32]}"` so the engine's per-job_type partial unique index collapses duplicate in-flight submissions; the POST handler additionally looks up an active (`Pending`/`Running`) request with the same tenant/format/filter-hash first and returns it instead of enqueuing (200 with the existing request), so the UI cannot stack duplicates by double-clicking. Two facts pin this asymmetry in Task 5's RED spec: a request in `Pending`/`Running` state DOES block a fresh POST of the same tenant/format/filter-hash (same request id returned, nothing enqueued), and a `Completed` request does NOT block it — a fresh POST after completion creates a NEW request id, because the engine hard-deletes the queue row on success and the partial unique index only ever collapses IN-FLIGHT duplicates. Permanent "never twice" semantics are intentionally NOT claimed: requesting the same export again after completion is legitimate.

**D4 — Filter snapshot is normalized, typed JSON.** `filters_json` stores `{"search":string|null,"statuses":[wire],"levels":[wire]}` — the output of the same normalizers the sync path uses (`TenantUserFilterQuery.NormalizeSearch/ParseStatuses/ParseLevels`), never raw query strings, and never `ids` (selection export stays synchronous). The worker rebuilds `ExportTenantUsersArgs` from this snapshot, so the export reflects exactly what the user saw. Sort order is fixed (`created_at desc, user_id desc` — the existing `FindExportRowsAsync` ordering), deliberately independent of the list page's sort: an export is a dataset, not a screenshot.

**D5 — Paging in the worker.** New service method `FindExportRowsPageAsync(tenantId, args, afterCreatedAt, afterUserId, pageSize)` on `ITenantUserQueryService` continuing the existing keyset (`orderby ua.User.CreatedAt descending, ua.UserId descending`), page size 1000, looped to exhaustion. Alternative: one unbounded `Take(cap)` query was rejected — a 250k-row materialization holds memory and a connection for minutes; keyset paging stays resumable and cancellation-friendly.

**D6 — Status transitions and failure causes.** All writes to the request row go through ONE service (`Modules/Users/Services/UserExportRequestService.cs`, `[Service(ServiceLifetime.Scoped)]`, discriminated-union results like `FindTenantUsersResult`): single-statement conditional UPDATEs (`WHERE id = $1 AND status = $expected`) make lost-lease re-runs safe. Row-count safety valve: `USER_EXPORT_JOB_MAX_ROWS` (default 250000) — exceeding it fails the job with a cause naming the cap and the next action ("narrow your filters"), never a silent truncation.

**Cap-trip fate (explicit choice, not a default).** When the cap trips mid-write, the worker (a) flushes and closes the file via the same `try/finally` pattern as `WriteCsvAsync` (`ExportTenantUsersAsStaff.Handle` does this for the response body), (b) **deletes the partial blob** via `IFileStorage.DeleteAsync` in a `finally` clause (a failure to delete is logged but does not mask the cap cause), and (c) returns `JobOutcome.PermanentFailure("exceeded USER_EXPORT_JOB_MAX_ROWS=…; narrow your filters and re-run")`. The request row's `error` field carries the same plain-words cause with the configured cap value. Rationale: the alternative (keep the partial file and surface "truncated") violates the owner rule 2026-08-22 §1.7 — the user must know what they get. A spec anchors this: `ItShouldDeleteThePartialArtifactAndReportTheCapWhenMaxRowsExceeded` writes 240k rows, sets the env cap to 100 for the spec, asserts the file is absent, the row is `Failed` with the cap-named cause, and the audit row is absent (no PII exfiltration happened).

**Terminal-failure hook (new use of `OnTerminalFailureAsync`).** The hook here is NOT a copy of the `EmailJobHandlerBase` pattern, which uses `OnTerminalFailureAsync` to write `email_log(PermanentlyFailed)` rows — `PasswordResetEmailJobHandler` does not override the hook at all, and `PublishPublicationJobHandler` uses it to transition a `Publication` to `Failed`. This lane extends the hook for a NEW purpose: persisting the `UserExportRequest` row's `Failed` state and its `error` cause from `context.LastError`, inside the engine's terminal transaction (F5). A throw inside the hook rolls back the DLQ insert; the job is retried whole. This is why the hook is the right seam: the row is the audit-of-record for "did the PII bulk-read happen" and that statement has to be written atomically with the DLQ row.

**D7 — Authorization, delivery, and retention.** Artifacts are written under `private/user-exports/yyyy/MM/<uuidv7>.csv|json` — a PRIVATE prefix the anonymous static middleware cannot resolve once this plan scopes the mount to the `uploads/` subtree — scoped root `Path.Combine(fileStorage.RootPath, "uploads")` WITH matching prefix `RequestPath = "/files/uploads"` (r5 decision, see Architecture §3 and Task 7) — and downloaded ONLY through the staff-gated `ExportArtifactForStaff` route. Three policy points the plan must nail before merge:

- **Authorization per download.** The `/files` mount is unauthenticated BY DESIGN (it serves staff-uploaded logos/avatars publicly, `Program.cs:258-269`; `CreateStaffUpload.cs` documents "world-readable by URL forever"). "UUID v7 + short expiry" is unguessability, not authorization, and a URL merely printed in an API response body grants nothing by itself. The plan therefore makes the artifact UNREACHABLE from the open mount twice over: exports are written under `private/user-exports/…` AND the static middleware itself is scoped to exactly the `uploads/…` tree in this plan (r5 decision: scoped ROOT plus MATCHING prefix `RequestPath = "/files/uploads"` — scoping the root while keeping `/files` strips only `/files` and double-counts `uploads/`; verified impact: both producers write only under `uploads/` via `SaveAsync` and serve `$"/files/{relativePath}"` URLs whose `relativePath` already begins `uploads/` — `CreateStaffUpload.cs:123,146` / `AttachPostImageForTenant.cs:153,250` — and every consumer pins or consumes the `/files/uploads/…` shape), so anything outside `uploads/` is unresolvable through the mount. Because the two halves are COUPLED, the gate spec walks the REAL end-to-end path instead of asserting either half in isolation: the export worker produces an artifact first, then the spec asserts BOTH sides on the artifact state the worker actually persisted (path regex pinned by Task 4's `ItShouldCompleteWithRowCountPersistedPathAndReadableArtifactWhenUsersMatch`) — the upload-tier control MUST return 200 through the fixed mount as an EXPLICIT assertion of the spec (never an implication), and anonymous retrieval THROUGH the static mount at the persisted path must return 404 — so a regression in either half, or simply a broken mount, turns the spec red (mutations A and B, Task 7). The ONLY read path for exports is `GET …/users/export-jobs/{requestId}/file`, handled by `ExportArtifactForStaff` and registered with `.WithPermission([AppPermissions.Staff.Users.LIST_FOR_TENANT])` — session-auth and permission filters run BEFORE the handler, so an unauthenticated call gets 401 and a logged-in staff without the right gets 403. The handler loads the request row, asserts `tenant_id` equals the route tenant (another tenant's staff → 404, no existence leak), asserts status `Completed` and `file_expires_at > now`, then streams `file_path` through the `IFileStorage.OpenReadAsync` method added in Task 4. Guessing or capturing the storage name is worthless: no HTTP route maps storage paths to bytes without a valid request id plus the permission. **Staff permission revocation mid-window:** if the requesting staff loses `LIST_FOR_TENANT` between completion and download, the gate returns 403 and the artifact sits untouched until the retention sweep deletes it. No read access after the right is gone.
- **No 1-year public cache.** `Program.cs:266-268` sets `Cache-Control: public, max-age=31536000, immutable` on EVERY `/files/*` response, so ANY artifact served through that mount inherits a one-year immutable cache no matter what else the plan does — a shared proxy would hold the PII long past `file_expires_at`. Because downloads flow exclusively through `ExportArtifactForStaff` (previous bullet), they never traverse the static middleware — and after the r5 scoping (root and prefix together) the mount could not even resolve a `private/` path if a future regression tried. The handler still sets `Cache-Control: private, no-store, max-age=0` and `Content-Disposition: attachment` explicitly on its own response. Spec anchor: `ItShouldSetPrivateNoStoreCacheControlOnTheArtifactDownload` (Task 6). Rejected alternative: mutating the mount's `OnPrepareResponse` lambda to discriminate by path — it hides the policy inside one lambda and cannot recall a copy a CDN already pinned under the immutable header.
- **Retention.** `file_expires_at = completed_at + USER_EXPORT_FILE_RETENTION_DAYS` (default 7 days). New system job `user-export-file-retention` (handler `Modules/Users/Jobs/ExportFileRetentionHandler.cs`): deletes expired blobs via `IFileStorage.DeleteAsync`, then prunes request rows older than `USER_EXPORT_REQUEST_RETENTION_DAYS` (default 30; the durable history is the audit log, per the junction/history rule in AGENTS.md). Seeded in `SystemJobDefinitionSeeder.GetDefinitions()` daily at 04:30 (staggered after the 04:00/04:15 sweeps), which `SyncSystemJobsJob` reconciles automatically. `LocalDiskFileStorage.DeleteAsync` has a TOCTOU window between `File.Exists` and `File.Delete` (no try/catch around the `File.Delete`); the retention handler's spec asserts a "file already gone" outcome as `JobOutcome.Succeeded` (idempotent retention), not `JobOutcome.Retry`. Honesty note: anything served under `/files` for NON-export files remains bearer-URL — that pre-existing public tier (logos, avatars) is untouched and out of scope; export artifacts are simply never placed on it, which is what closes their exposure. The r5 mount rescoping (root and prefix together) is itself a scope change to a shared component, so its blast radius is audited, not asserted: zero production consumers exist outside `uploads/` (producers `CreateStaffUpload.cs` / `AttachPostImageForTenant.cs` write only there and serve `/files/uploads/…` URLs; validators `TenantValidationRules` / `AccountProfileValidationRules` and `ServedUploadPath.ExtractOrNull` recognize only `/files/uploads/…`; the global rate-limit floor excludes the `/files` path prefix, which still covers the narrower mount; front uses API-returned `/files/uploads/…` URLs — evidence `.dump/citations-r5.md` C2/C8). The single affected consumer is test-only: the traversal-control file in `CreateStaffUpload.Spec.cs` moves under `uploads/`. If private signed downloads are ever wanted FOR THE PUBLIC TIER TOO, that's an `IFileStorage` contract extension, filed separately as `follow-up lv2`.

**D8 — Permissions, rate limit, audit.** POST/GET routes sit on the existing users group with `.WithPermission([AppPermissions.Staff.Users.LIST_FOR_TENANT])` — the exact gate the sync export uses today; splitting a dedicated `users.export_for_staff` permission multiplies seeder churn without a security boundary gain (the data read is the same bulk read). The staff users group already declares `.RequireRateLimiting(ApiRateLimitPolicies.AuthenticatedDefault)` (`UserEndpointsForTenantAsStaff.cs`), so every new route inherits the default. The new routes MUST override on each `MapXxx(...)` call:
- `POST /export-jobs` → `.RequireRateLimiting(ApiRateLimitPolicies.TenantExport)` (same bucket as the sync export, today's `ExportTenantUsersAsStaff`).
- `GET /export-jobs` (list) and `GET /export-jobs/{requestId}` → `.RequireRateLimiting(ApiRateLimitPolicies.HeavySearchList)`. The plan's r1 phrasing ("reads use HeavySearchList") was wrong without this explicit per-endpoint call; without it the GETs would inherit the group default `AuthenticatedDefault` and a user could spam polls unthrottled.
Each assignment is also pinned as a new `[InlineData("CreateTenantUserExportJobForStaff", ApiRateLimitPolicies.TenantExport)]` and `[InlineData("FindTenantUserExportJobsForStaff", ApiRateLimitPolicies.HeavySearchList)]` row in `Lib/RateLimiting/EndpointRateLimitAssignments.Spec.cs`; that row is listed explicitly in Task 5 RED and Task 6 RED below. Audit: ONE row, `AuditActions.TenantUserExported` (constant already exists in `Modules/AuditLogs/Entities/AuditLog.cs`), written by the worker on completion with details `{requestId, rowCount, filters, format}` — the audited event is the PII bulk-read having happened; the request row itself records intent/request. The sync path's audit stays untouched.

**Wire conventions:** camelCase JSON fields, snake_case query params; `POST` success → 201 `Created<UserExportRequestResult>`; poll/list → 200; malformed tenant GUID → 400 `TypedProblems.BadRequest`; unknown request id → 404; invalid body → 422 with stable keys. `UserExportRequestResult`: `{id, status, format, rowCount, error, fileUrl, fileExpiresAt, createdAt, updatedAt}` — `fileUrl` present only when `Completed` and unexpired, and it always points AT the gated download route (`…/users/export-jobs/{requestId}/file`), never at the `/files` static mount; `error` present only when `Failed` (cause in plain words, next action included).
