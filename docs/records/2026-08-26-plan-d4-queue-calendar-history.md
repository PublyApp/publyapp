# D4 — Queue + Calendar + History UI + Retry: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land Epic D step 8 (#647, part of #631; spec: `docs/records/2026-08-22-spec-epic-d-publishing-scheduling.md` §D4): wire the tenant **Queue** page to D3's `GET /posts/publications?from=…&to=…&status=…` tenant-scoped date-windowed read, wire the tenant **Calendar** to the same D3 endpoint in month form, wire the tenant **History** page to D2's `GET /publishing/publications` keyset read as-is, add the **Retry** button on `Failed` rows (status pill + plain-words cause + next action) per spec §4, and route the retry through the existing `IPublicationStatusTransitionService.RescheduleToNowAsync` — never a direct status write (the `PublicationArchitecture.Spec` ratchet forbids it). The plan covers the architecture-guard extensions that pin the retry path to the transition service, the REUSE of develop's existing `StatusPill` primitive (verified on `origin/develop` — see Prerequisites) by the queue/calendar pages, and the merge order **D2 → D3 → D4** (D4 rebases onto develop after both D2 and D3 land — the Queue/Calendar pages cannot be wired without D3's `IPublicationService.FindScheduledAsync` + the date-windowed read it returns).

**Architecture:** D4 is mostly a wiring pass. The retry endpoint is a new `POST /publications/{publicationId}/retry` route on the existing `Routes.Publishing.ForTenant` group (D2 PR #1457 IN-FLIGHT on `origin/lane/wt-645b` tip `a55da71bb` — read branch, NOT develop; D3 PR #1450 IN-FLIGHT on `origin/lane/wt-646b` tip `7fefce10c` — read branch, NOT develop; merged-on-develop versions are NOT available), gated by `AppPermissions.Tenant.Posts.PUBLISH`; it calls a thin `RetryPublicationService.RetryAsync(args, ct)` that **only** re-issues the trust-boundary enqueue and **only** writes status through `IPublicationStatusTransitionService.RescheduleToNowAsync` (D1, on `origin/develop` tip `26896f251`: `ReschedulePublicationToNowArgs` record at line 30 and the method at line 171 of `apps/api/Modules/Publishing/Services/PublicationStatusTransitionService.cs`, verified 2026-08-26 against develop tip `26896f251` — always re-confirm with `git grep -n "RescheduleToNowAsync" origin/develop -- apps/api/Modules/Publishing/Services/PublicationStatusTransitionService.cs` before relying on the numbers; D2/D3 may shift them). The Queue and Calendar pages consume D3's `GET /posts/publications?from=…&to=…&status=…` read through the regenerated Kiota client (D3 PR #1450, IN-FLIGHT on `origin/lane/wt-646b`); the History page consumes D2's `GET /publishing/publications` keyset read. D4 does NOT invent a new read shape and does NOT extend D2's `PublicationListItem` DTO — D3's `ScheduledPublicationItem` already carries `ScheduledAtUtc` + `ScheduledAtLocal` + `TimeZone` for the Queue/Calendar render. All UI failures are surfaced through `getFailureMessage(toApiFailure(error), …)` (exported from `packages/shared-ts/src/lib/api-failure/to-api-failure.ts` at develop tip `26896f251:298`; the repo rule, enforced by `publy/no-manual-response-message-translation`).
