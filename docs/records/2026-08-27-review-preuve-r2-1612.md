## 1. What R2 changes — syntax analysis

The R1 guard scanned each file **line by line** (`readFileSync(...).split('\n')`) and applied a regex `REEXPORT_SHARED_TS`. Any multi-line construct was **structurally invisible**. The most idiomatic form — a named re-export spread across multiple lines — slipped entirely through:

```ts
export {
  foo,
} from '@org/shared-ts/lib/...';
```

R2 replaces this with **syntax analysis** via ts-morph (`import { ts } from 'ts-morph'`): each file is parsed into a real AST, and the guard visits the `ExportDeclaration` nodes (and recursively all nodes). This catches all forms by construction, instead of enumerating them:

- `export { a, b } from '...'` — single-line **and** multi-line;
- `export type * from '...'` — type re-export;
- `export * as ns from '...'` — namespace re-export with alias;
- `export * from '...'` — namespace re-export;
- `export type { a } from '...'` — named type re-export;
- `import ... from '...'` / `import type ... from '...'` / `import('...')` — **inspected** (the walk sees every form), but **not flagged**: a direct import — static or dynamic — is the desired path, not a second one.

The only flagged nodes are `ExportDeclaration`s whose module specifier matches `@org/shared-ts/(lib|utils|validations|types)` — this is the only construct that actually creates a **second** resolvable path to the same module.

## 5. Regression test — the guard analyzes syntax, not text

The following permanent test would fail if the guard reverted to a line-by-line scan:

```
REGRESSION: guard inspects the AST, not lines — multi-line form must be caught (not blank-line-skipped)
```

It reintroduces the multi-line form (test line 12, `MULTILINE_NAMED_SHIM_BODY`) and requires a match. A line-by-line scan would **never** see the declaration `export {\n foo,\n} from '...'` as a single `export ... from '...'` statement on one line — it would scan three separate lines, none matching the pattern. This test therefore blocks any regression.

## What is proven / not proven

Proven:
- The guard detects a multi-line re-export (the form that blocked R1) — RED→GREEN (§2, form 1, test `RED: multi-line named re-export ...`).
- The guard detects `export type *`, `export * as ns`, `export type { X }` — RED→GREEN (§2, forms 2-4, tests `RED: ...`).
- The extension detects a reintroduction in `packages/shared-ts/src` — RED→GREEN (§3).
- No false positives on the real tree after R2 (806 files, GREEN).
- The regression test `REGRESSION: ... AST, not lines ...` blocks any return to line-by-line scanning.
- All import forms (`import`, `import type`, `import('...')`) are **inspected** by the AST walk but produce no false positive — these are direct imports, the desired path.

Not proven by this work (assumed limits):
- The guard only covers re-exports `export ... from '@org/shared-ts/(lib|utils|validations|types)'`. A second path created by a TS alias outside this pattern, or by a build redirection outside source (e.g. `tsconfig` paths), is out of scope — that is not the defect #1533 targets, and the guard header documents it.
- The CI branching (`pnpm test` → `check:shared-ts-import-paths` → `node --test ...`) is unchanged and now runs all 16 tests; real CI validation happens on the PR (front-e2e 4/4 by CI, per the verification policy: no local e2e stack).
