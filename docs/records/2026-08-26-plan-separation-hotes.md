### 3.3 The guard that prevents drift (to be delivered WITH the first tranche, not after)

New architecture spec `packages/shared-cs/Lib/CorePurity.Spec.cs` (compiled in existing runner, cf. T2), two axes:
1. **Csproj**: `PublyApp.Core.csproj` must contain neither `<FrameworkReference Include="Microsoft.AspNetCore.App" />`, nor `Sdk="Microsoft.NET.Sdk.Web"`, nor any PackageReference whose name starts with `Microsoft.AspNetCore.` — parsed from the real file (guard pattern C10/C11: read the actual source, not a copy). **Named carve-out (TWO packages explicitly allowed, decided in ROUND 3 + ROUND 4 — see §3.3bis/§3.3ter):** `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` (ROUND 3) **and** `Microsoft.AspNetCore.DataProtection` (ROUND 4 — the parent namespace, carried by `CredentialProtector.cs` in T5) are the ONLY exceptions allowed by this guard. Any other PackageReference whose name starts with `Microsoft.AspNetCore.` makes the spec go RED (axis 1), with no generic prefix relaxation. Reason (written justification, identical for both): these packages bring NO web hosting surface into Core. `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` contains only `IDataProtectionKeyContext`, the `DataProtectionKey` entity and its `IEntityTypeConfiguration` (cf. `DataProtectionKeyConfiguration.cs:1`, citation C38) — *persistence of a key ring* plugged into `DbContext`. `Microsoft.AspNetCore.DataProtection` (parent) contains only `IDataProtectionProvider` / `IDataProtector` and key ring abstractions — **zero** dependency on the ASP.NET Core pipeline (no `WebApplication`, no middleware, no routing, no MVC, no HTTP result types). Both are pure *encryption / persistence*, on the same footing as `Microsoft.EntityFrameworkCore` itself. Nothing in these packages is an endpoint, a middleware, a route filter, or a web host: they therefore do not introduce the "web junk drawer" that §3.2 forbids. The exception is *explicitly* scoped to the TWO named packages; the `Microsoft.AspNetCore.` prefix remains forbidden for everything else, and spec axis 1 turns red if another package with that prefix is added (red/green proof in §3.3bis/§3.3ter).
2. **Source**: scan Roslyn (real precedents: `JobEnqueueBoundary.Spec.cs` under `apps/api/Infrastructure/Jobs/` — lexed by `Microsoft.CodeAnalysis.CSharp`, C35; `ApiFactoryHostedServiceGuard.Spec.cs` under `apps/api/Lib/Architecture/` — resolves real container services and bans a type, C35; the path `Lib/Architecture/JobEnqueueBoundary.Spec.cs` cited at r1 was wrong) of `packages/shared-cs/**/*.cs` excluding `*.Spec.cs`: banned `using Microsoft.AspNetCore.*;` **except the TWO named carve-outs `using Microsoft.AspNetCore.DataProtection.EntityFrameworkCore;` (ROUND 3) AND `using Microsoft.AspNetCore.DataProtection;` (ROUND 4, parent namespace)** — paired with the csproj carve-out §3.3 axis 1. (Note: `CredentialProtector.Spec.cs` also carries `using Microsoft.AspNetCore.DataProtection;` but is excluded from the scan by the `*.Spec.cs` rule of T2 — it therefore does not trip the guard; `ImpersonationService.Spec.cs` carries `Microsoft.AspNetCore.Http.HttpContextAccessor` and is similarly excluded. The spec must prove it detects its failure via a **realistic mutation**, not just "delete the guard → red" (which only proves it reads itself):
   - *Required red proof (axis csproj)*: add `<FrameworkReference Include="Microsoft.AspNetCore.App" />` to `PublyApp.Core.csproj` (reference forbidden by axis 1) and require the spec run **RED**; remove the reference before the tranche commit. ### 3.3bis Resolution of the T3 ↔ §3.3 conflict (ROUND 3 — decision made, written BEFORE T3)

**Conflict (verified, citations C37-C39).** `AppDbContext` (in `Data/DbContext/`) implements `IDataProtectionKeyContext` and uses `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` (`AppDbContext.cs:27` declares `: … DbContext, IDataProtectionKeyContext`, :282 and :308 reference `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore.DataProtectionKey`, citation C37; `DataProtectionKeyConfiguration.cs:1` has `using Microsoft.AspNetCore.DataProtection.EntityFrameworkCore;`, citation C38). This package is referenced in `apps/api/PublyApp.Api.csproj:33` (`<PackageReference Include="Microsoft.AspNetCore.DataProtection.EntityFrameworkCore" />`, citation C39). T3 moves **all of `Data/`** (including `AppDbContext` + `DataProtectionKeyConfiguration`) to `packages/shared-cs`. But §3.3 axis 1 (before ROUND 3) forbade any PackageReference `Microsoft.AspNetCore.*` in Core. T3 as written therefore produced a Core that either violated its own guard or failed to compile (the `IDataProtectionKeyContext`/`DataProtectionKey` type no longer exists without the package). No mention of this interaction existed in the plan (a `grep -nE 'DataProtection|IDataProtectionKeyContext'` on the document returned only one hit, on the EF reflection of §3.1 — R2 MAJOR).

**Decision (chosen option: (a)).** Core references `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` and §3.3 axis 1 is relaxed **for THIS package ONLY**, by name (cf. carve-out in §3.3 axis 1). `AppDbContext` **keeps** `IDataProtectionKeyContext` and its `DataProtectionKey`/`DataProtectionKeyConfiguration` in Core — they migrate integrally with `Data/`.

**Argument (why (a) and not (b)).**
- (a) keeps a **single, shared** Data Protection key ring between the two hosts (api + worker): it's database state (`data_protection_keys`), not a web surface. If we chose (b) — extract the `DataProtectionKey` config into an `IEntityTypeConfiguration` left in the web host — Core's `DbContext` would no longer declare `IDataProtectionKeyContext` or the `DbSet`, and the key ring would either be duplicated per host (two divergent `DbContext` mapping the same table) or orphaned (no host persists the ring). But the worker host itself needs the key ring (job payload encryption, infrastructure secrets): separating the entity from Core would break inter-host encryption consistency. (a) is therefore the only choice that preserves Core's **shared data semantics**.
- The `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` package carries **zero** dependency on the ASP.NET Core pipeline (no `WebApplication`, no middleware, no route binding). It is pure *persistence code*, on the same footing as `Microsoft.EntityFrameworkCore` itself. The §3.3 prohibition targets the "web junk drawer" drift, not key ring storage primitives. The relaxation is therefore harmless for the §3.2 boundary, provided it is **explicitly** scoped to the package and not the prefix.
- (b) would also force a redundant `IEntityTypeConfiguration` per host (api and worker) that re-maps `data_protection_keys` — duplicating the config violates the "one entity = one co-located config" principle of §3.1/§3.4 (sites 2/7). (a) respects this principle: the config stays unique, in Core.

**Required red/green proof (paired with the carve-out, to be wired into `CorePurity.Spec.cs` — axis 1 csproj + axis 2 source).**
- *GREEN required (carve-out `EntityFrameworkCore` allowed)*: with `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` present (and NO other `Microsoft.AspNetCore.*` reference) in `PublyApp.Core.csproj`, spec axis 1 runs **GREEN** — the package name is explicitly added to the axis 1 named allow-list.
- *GREEN required (carve-out parent `DataProtection` allowed — cf. §3.3ter ROUND 4)*: with `Microsoft.AspNetCore.DataProtection` present (and NO other `Microsoft.AspNetCore.*` reference besides the `.EntityFrameworkCore` carve-out) in `PublyApp.Core.csproj`, spec axis 1 runs **GREEN** — the parent package name is the SECOND named member of the allow-list. (Mutation `using Microsoft.AspNetCore.DataProtection;` in a Core source file → **no** violation, GREEN axis 2 — source-side counterpart of the parent carve-out.)
- *RED required (any other package with the prefix trips)*: adding `Microsoft.AspNetCore.Mvc` (or `Microsoft.AspNetCore.Authentication`, or any other `Microsoft.AspNetCore.*` except the TWO carve-outs) as a PackageReference to `PublyApp.Core.csproj` → spec axis 1 runs **RED**. The named allow-list contains ONLY `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` **AND** `Microsoft.AspNetCore.DataProtection`; any other entry with the prefix is rejected. This is the mutation a lane would actually write if it "forgot" that only the DataProtection exceptions are permitted, and that no generic prefix relaxation exists.
- *GREEN required (carve-out `using` `.EntityFrameworkCore` allowed — source axis)*: a Core file containing `using Microsoft.AspNetCore.DataProtection.EntityFrameworkCore;` (exactly the carve-out, e.g. the moved `AppDbContext.cs`) → **no** violation (GREEN), because the namespace is in the axis 2 named allow-list. This is the source-side counterpart of the csproj carve-out: without it, axis 2 would trip on legitimate Core files (AppDbContext / DataProtectionKeyConfiguration) and option (a) would be contradictory.
- *GREEN required (carve-out `using` `.DataProtection` parent allowed — source axis, ROUND 4)*: a Core file containing `using Microsoft.AspNetCore.DataProtection;` (exactly the parent carve-out, e.g. the `CredentialProtector.cs` moved in T5) → **no** violation (GREEN), because this namespace is the SECOND named member of the axis 2 allow-list. This is the source-side counterpart of the parent carve-out: without it, axis 2 would trip on `CredentialProtector.cs` in T5 (the fifth case of the ROUND 4 brief), making option (a) ROUND 4 contradictory.
- *RED required (any other `using` with the prefix trips — source axis)*: a Core file containing `using Microsoft.AspNetCore.Mvc;` (or any other `Microsoft.AspNetCore.*` except the TWO carve-outs) → non-empty violations (RED). The axis 2 named allow-list contains ONLY `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` **AND** `Microsoft.AspNetCore.DataProtection`; any other `using` with the prefix is rejected. This is the mutation a lane would actually write by "forgetting" that only these namespaces are permitted.
- All these mutations are removed from the csproj before the tranche commit; they serve only as proof of non-regression of the guard.

**Sequencing (so no runner hits the conflict mid-way).** The decision above is materialized by an **explicit T3-pre task**, inserted BEFORE T3 in Phase A (cf. §4: T3-pre just before T3). It delivers the `PublyApp.Core.csproj` *with* the carve-out PackageReference + the named allow-list in `CorePurity.Spec.cs` axis 1 already in place, and verifies the paired red/green proof, **before** T3 moves `Data/`. ### 3.3ter Resolution of the T5 ↔ §3.3 conflict (ROUND 4 — fifth case, decision made, written BEFORE T5)

**Conflict (verified, real exhaustive scan `.dump/citations-r4.md`).** `Modules/SocialAccounts/Services/CredentialProtector.cs:1` carries `using Microsoft.AspNetCore.DataProtection;` — the **parent namespace**, DISTINCT from `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` (the ROUND 3 carve-out covered only the `.EntityFrameworkCore` sub-namespace, not the parent). `CredentialProtector` depends on `IDataProtectionProvider` (injected via ctor, `CredentialProtector.cs:8-10` — `private readonly IDataProtectionProvider _dataProtectionProvider;`) to encrypt/decrypt social account secrets (methods `Protect`/`Unprotect`, `Microsoft.AspNetCore.DataProtection` only). But §3.1 lists `Modules/<Domain>/Services/` among the content ALLOWED to enter Core (the lot consumed by both hosts), and **T5 explicitly moves this folder to Core** — `CredentialProtector.cs` is therefore squarely within T5's scope. The plan (rounds 1-3) mentioned THIS file nowhere: not in the carve-out, not in the "Scope (out of section)". It is an **oversight**, not a declared out-of-scope item (unlike the two `[FromQuery]` primitives of round 3, which were explicitly out-of-scope). The ROUND 4 reviewer found it by independent scan: the parent `Microsoft.AspNetCore.DataProtection` `using` (1 file) adds to the 3 covered `.EntityFrameworkCore` files — making 4 Core files carrying a `using Microsoft.AspNetCore.*` in total, not 3.

**Decision (chosen option: (a) — extend the source carve-out to the parent namespace `Microsoft.AspNetCore.DataProtection`).** Core explicitly references **BOTH** packages `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` (ROUND 3) **and** `Microsoft.AspNetCore.DataProtection` (ROUND 4), and §3.3 axes 1/2 are relaxed **for THESE TWO packages by name** (cf. carve-out in §3.3 axis 1/axis 2). `CredentialProtector.cs` **enters Core INTEGRALLY with T5** — it does not need to stay in `apps/api` (option (b)) or be rewritten (option (c)).

**Argument (why (a) and not (b) nor (c)).**
- *Factual nature of the parent namespace*: `Microsoft.AspNetCore.DataProtection` (parent) contains ONLY the encryption/key ring abstractions — `IDataProtectionProvider`, `IDataProtector`, `DataProtectionProvider` — and ZERO web hosting surface (no `WebApplication`, no middleware, no routing, no MVC, no HTTP result types). It is pure *encryption*, on the same footing as `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` (the ring persistence) already carved-out: the two together form the complete Data Protection primitive, and neither is the "web junk drawer" that §3.2 forbids. The relaxation remains **explicitly** scoped to the TWO named packages, never to the `Microsoft.AspNetCore.` prefix (`[FromQuery]` / `Microsoft.AspNetCore.Mvc` stays out of the carve-out, a distinct conflict to be handled by the task that moves the primitives).
- (b) — leaving `CredentialProtector.cs` in `apps/api` — would break the §3.1 entry rule ("consumed by ≥ 2 hosts, OR domain/data access"): `CredentialProtector` is a **domain** service of SocialAccounts (interface `ICredentialProtector` consumed by `SocialAccountService` and the Bluesky providers, all moved to Core with T5 — cf. grep `ICredentialProtector` in `Modules/SocialAccounts/Services/SocialAccountService.cs:131/136` and `Modules/SocialAccounts/Providers/Bluesky/BlueskySessionProvider.cs:29/35`). Leaving it in api would create a **circular** `apps/api → Core` dependency (Core's domain service `SocialAccountService` would have to re-import the api service) or force a duplicate. (a) keeps the unique domain service, in Core, consistent with the §3.2 boundary.
- (c) — rewriting `CredentialProtector` to no longer depend on Data Protection — is not viable without changing semantics: encrypting social secrets IS the service's responsibility (the worker itself needs to decrypt these secrets, as with the key ring in ROUND 3); a rewrite would introduce a dependency on another encryption mechanism or on the web host, worse than the status quo. (a) reuses the Data Protection key ring **already shared** between api + worker (built in ROUND 3) — it is the choice that preserves Core's **shared data semantics**, exactly like (a) ROUND 3 for `DataProtectionKey`.
- The relaxation is **harmless** for the §3.2 boundary: `Microsoft.AspNetCore.DataProtection` carries zero dependency on the ASP.NET Core pipeline, so it introduces no "web junk drawer" drift. It is scoped to the named package only, never to the prefix.

**Red/green proof (update of §3.3bis to cover the parent carve-out).** The GREEN bullets "carve-out parent `DataProtection` allowed" (csproj axis 1) and GREEN "carve-out `using` `.DataProtection` parent allowed" (source axis 2) are added in §3.3bis: with `Microsoft.AspNetCore.DataProtection` alone (besides the `.EntityFrameworkCore` carve-out) present, the spec runs GREEN; `using Microsoft.AspNetCore.DataProtection;` in a Core file → no violation. The RED mutation remains "any other `Microsoft.AspNetCore.*` except the TWO carve-outs". These mutations are removed before the T3-pre tranche commit (which now wires BOTH packages into the named allow-list, cf. §4 T3-pre).

**Sequencing.** The named allow-list (axis 1 csproj + axis 2 source) is extended to BOTH named packages in **T3-pre** (which delivers the `PublyApp.Core.csproj` with `Microsoft.AspNetCore.DataProtection.EntityFrameworkCore` **AND** `Microsoft.AspNetCore.DataProtection` + the allow-list), therefore **before T5**. Thus T5 inherits an already-consistent guard and `CredentialProtector.cs` enters Core without tripping the spec (nor violating guard axis 1, since the parent package is referenced there by name). No runner hits the conflict mid-way.
