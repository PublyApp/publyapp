How claiming works in Postgres (the key idea)
There are two common ways:

Approach A: FOR UPDATE SKIP LOCKED (very common, very good)
Worker starts a DB transaction

Selects due rows and locks them

Others skip locked rows automatically

The logic is:

“Give me the next 50 posts due now, lock them, and I’ll process them.”

Why it’s great: No race conditions; scales well.

Approach B: Atomic UPDATE … RETURNING (also great)
One SQL statement updates N due rows from scheduled → processing

Returns which rows it claimed

Why it’s great: Simple, fast, no double-claim.

That’s why you store locked_until.

Example:

worker claims a job with locked_until = now + 5 minutes

if it dies, another worker can reclaim after lock expiry

1. Stale Claim Recovery
With direct execution, if a worker crashes mid-job, the post is stuck in processing forever. You need a recovery mechanism:
csharppublic class RecoverStaleJobsJob : IJob
{
    public async Task Execute(IJobExecutionContext context)
    {
        // Jobs stuck in "processing" for more than 10 minutes = assumed crashed
        var staleThreshold = DateTime.UtcNow.AddMinutes(-10);
        
        var recovered = await _db.ScheduledPosts
            .Where(p => p.Status == PostStatus.Processing)
            .Where(p => p.ClaimedAt < staleThreshold)
            .ExecuteUpdateAsync(s => s
                .SetProperty(p => p.Status, PostStatus.Scheduled)
                .SetProperty(p => p.ClaimedAt, (DateTime?)null)
                .SetProperty(p => p.RetryCount, p => p.RetryCount + 1));

        if (recovered > 0)
            _logger.LogWarning("Recovered {Count} stale jobs", recovered);
    }
}
Schedule this every 5 minutes. Without it, crashed workers leave orphaned jobs.

2. Worker Pool Pattern (Even Without RabbitMQ)
If your Quartz job executes posts synchronously, you process one at a time. For parallelism without a broker:
csharppublic class PublishDuePostsJob : IJob
{
    private readonly SemaphoreSlim _concurrencyLimit = new(10); // Max 10 parallel

    public async Task Execute(IJobExecutionContext context)
    {
        var duePosts = await ClaimDuePostsAsync(batchSize: 50);
        
        var tasks = duePosts.Select(async post =>
        {
            await _concurrencyLimit.WaitAsync();
            try
            {
                await PublishPostAsync(post);
            }
            finally
            {
                _concurrencyLimit.Release();
            }
        });

        await Task.WhenAll(tasks);
    }
}
This gives you parallelism within a single worker process. Add this when you need throughput.

### 4. The "No Outbox" Trade-off

GPT said "jobs table is your outbox" — true, but there's a subtle difference:

**With MassTransit outbox:**

Transaction {
    Update business data
    Write to outbox
} → Commit
// Later: outbox publisher sends message
// Consumer executes independently
**With direct execution:**

Transaction {
    Claim job (update status)
} → Commit
// Then: execute API call
// Then: update status again
The difference: with direct execution, **the API call is outside the transaction**. If the API succeeds but the final status update fails, you have the idempotency problem we discussed.

This is why idempotency (Section 5 of my doc) is even MORE critical without a broker. You don't have message-level deduplication to save you.

Claim jobs due now (jobs.run_at <= now()) using FOR UPDATE SKIP LOCKED

Execute job handler (publish post, refresh token, cleanup, etc.)

Mark job done OR reschedule with backoff

Update scheduled_posts status appropriately (published / failed / etc.)

D) Crash safety (stale claim recovery)
If a worker dies mid-job, the job must become available again. You do that via:

locked_until on each job claim (lease)

a periodic recovery job (Quartz) or a query in the worker loop that requeues expired leases

This is exactly what Claude called out.

2) “Pure Postgres” schema and queries (recommended baseline)
A) Tables
scheduled_posts (business schedule)
what the user wants (publish at time T)

Key columns:

publish_at_utc timestamptz not null

status text not null (scheduled|queued|published|failed|canceled)

retry_count int not null default 0

last_error text null

idempotency_key text not null (per platform/account+post; unique where appropriate)

jobs (execution queue)
what your system needs to execute

Key columns:

type text not null (e.g., publish_post)

payload jsonb not null (keep small: IDs only)

run_at timestamptz not null default now()

status text not null (queued|processing|done|failed)

attempts int not null default 0

locked_by text null

locked_until timestamptz null

last_error text null

created_at timestamptz not null default now()

Indexes:

(status, run_at) for fast “due jobs” lookup

optionally partial index: where status='queued'

This split makes you future-proof: today it’s Postgres-only; later you can replace jobs with a broker if needed without rewriting “scheduled_posts”.

B) Claim due scheduled posts (Quartz dispatcher)
Do it in a transaction:

-- 1) lock due rows
WITH due AS (
  SELECT id, post_id, tenant_id
  FROM scheduled_posts
  WHERE status = 'scheduled'
    AND publish_at_utc <= now()
  ORDER BY publish_at_utc
  FOR UPDATE SKIP LOCKED
  LIMIT $1
)
-- 2) mark them queued (or processing if you execute immediately)
UPDATE scheduled_posts sp
SET status = 'queued'
FROM due
WHERE sp.id = due.id
RETURNING due.id, due.post_id, due.tenant_id;
Then insert jobs:

INSERT INTO jobs (type, payload, run_at, status)
VALUES
('publish_post', jsonb_build_object('scheduledPostId', $1), now(), 'queued');
(You can batch insert.)

Optional wake-up:

NOTIFY jobs_wakeup;
C) Worker claims jobs (the “trigger”)
This is how workers “know” there’s work:

WITH picked AS (
  SELECT id
  FROM jobs
  WHERE status = 'queued'
    AND run_at <= now()
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED
  LIMIT $1
)
UPDATE jobs j
SET status = 'processing',
    locked_by = $2,
    locked_until = now() + interval '5 minutes'
FROM picked
WHERE j.id = picked.id
RETURNING j.id, j.type, j.payload, j.attempts;
If RETURNING returns 0 rows → no work right now.

D) Mark success / failure
Success:

UPDATE jobs
SET status='done',
    locked_by=null,
    locked_until=null,
    last_error=null
WHERE id=$1;
Failure with retry (simple exponential backoff example):

UPDATE jobs
SET status='queued',
    attempts = attempts + 1,
    run_at = now() + (interval '2 seconds' * (2 ^ LEAST(attempts, 10))),
    locked_by=null,
    locked_until=null,
    last_error=$2
WHERE id=$1;
After max attempts, mark failed:

UPDATE jobs
SET status='failed',
    locked_by=null,
    locked_until=null,
    last_error=$2
WHERE id=$1;
E) Stale claim recovery (Claude’s point #1)
This is essential.

You can run this as a Quartz job every 5 minutes:

UPDATE jobs
SET status='queued',
    locked_by=null,
    locked_until=null,
    run_at = now(),
    last_error = COALESCE(last_error,'') || E'\nRecovered stale lease at ' || now()::text
WHERE status='processing'
  AND locked_until < now();
Same idea applies to scheduled_posts if you ever mark them processing directly.

3) Parallelism: where it should live
Claude suggested parallelism inside the Quartz job. That works, but the more scalable pattern is:

Quartz: claim + enqueue jobs

Workers: parallel execute jobs (N workers, M concurrency each)

So you get:

better draining under load

smoother scaling (just add workers)

Quartz stays fast and reliable

4) Deployment: one service or two?
Do this for simplicity + future-proofing:

✅ One PublyApp.Worker service, multiple replicas
Each instance runs:

worker loop (always on)

Quartz (only if it wins advisory lock)

Advisory lock leadership
At startup, try:

SELECT pg_try_advisory_lock(424242);
if true: enable Quartz scheduling

if false: disable Quartz; keep worker loop running

This gives you HA scheduler without split services.

5) Direct answer to the subtle “outbox trade-off” Claude mentioned
He’s right: with direct execution, the external API call is outside the DB transaction.

That’s why you must have idempotency keys for publish operations.

Practical pattern:

before calling platform API, ensure you have a stable idempotency_key

store platform’s returned platform_post_id in DB

if a retry happens and the platform already has the post, you detect and treat as success
