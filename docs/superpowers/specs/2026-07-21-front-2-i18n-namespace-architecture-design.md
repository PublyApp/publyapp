# front-2 i18n: Namespace Architecture + Per-Route Lazy Loading — Design (DRAFT for review)

**Status:** APPROVED by owner (2026-07-21). Implemented via
`docs/superpowers/plans/2026-07-21-front-2-i18n-p1-namespaces.md`.

**Issue:** part of #904 (the de-RPC unblock is a separate PR already in flight).

**Goal (one sentence):** Replace front-2's single bundled-and-refetched `common` namespace
with a proper namespace taxonomy loaded **per route, on demand, active-language-only,
SSR-preloaded (no flash)** — so translations scale as namespaces grow without bloating the
initial bundle or shipping inactive languages.

---

## 1. Problem & current state

- Today front-2 has **3 namespaces, all global**: `common` (catch-all), `zod` (validation),
  `response-message` (API messages). All load on every route.
- Resources are **statically bundled** (`i18n.client.ts`/`i18n.shared.ts` import all of
  en+fr) and — the bug — **refetched via a per-nav server function** (fixed in the unblock PR).
- `common` is a monolith seeded when the project started; the owner wants it split into
  properly-scoped namespaces now.

## 2. Namespace taxonomy

Grounded in the API modules (`AuditLogs, Auth, Impersonations, Invitations, Messaging,
Permissions, Profiles, Projects, SystemNotices, Tenants, Uploads, Users`) and the front-2
route tree.

**Global (always loaded, every route):**
| Namespace | Source | Contents |
|---|---|---|
| `common` (slimmed) | front-2-local | app chrome, nav, layout, generic actions/labels, error-view copy, shared table/empty-state text |
| `zod` | shared-ts (generated) | validation messages — stays shared, generated by `generate-zod-i18n-map.mjs` |
| `response-message` | shared-ts | API response/error text — mirrors backend keys, used by every mutation |

**Feature/route-scoped (front-2-local, lazy per route):**
| Namespace | Route subtree(s) |
|---|---|
| `auth` | `/login`, `/signup`, `/reset-password`, `/verify-email`, `/accept-invitation` |
| `staff-users` | `/staff/staff-users*` |
| `tenants` | `/staff/tenants*` |
| `dashboard` | `/staff/dashboard*` |
| `profiles` | profile screens (staff + tenant) |
| `permissions` | permissions screens |
| `invitations` | invitation flows |
| `audit-logs` | audit-log screens |
| `system-notices` | system-notice screens |
| `impersonations` | impersonation UI |
| `tenant-portal` | tenant post-login surface |

Namespaces are kebab-case, mirroring feature/route. `defaultNS` stays `common`. (Exact set
is refined per migration phase; add a namespace only when its screen exists.)

## 3. Source ownership (front-2-local, old front untouched)

- `zod` + `response-message` stay in **shared-ts** (genuinely shared + generated); front-2
  keeps consuming them as globals. **Old front is not touched.**
- `common` and every feature namespace become **front-2-local** JSON:
  `apps/front-2/src/i18n/locales/{en,fr}/{namespace}.json`. front-2's `common` is seeded from
  today's shared-ts `common`, then feature keys are extracted out into feature namespaces.
- Old front keeps using shared-ts `common` unchanged → zero blast radius on the retiring app.
  Minor duplication of truly-shared `common` keys during the migration window is accepted.

## 4. Loading architecture (TanStack Start)

- **i18next backend backed by Vite dynamic import.** A namespace→loader registry whose
  `read(lng, ns)` dynamic-imports the JSON chunk for `(ns, lng)`; Vite emits each as a hashed,
  separately-cacheable chunk. (`i18next-resources-to-backend`, a tiny official plugin, or a
  ~15-line custom backend. Some namespaces resolve to shared-ts, some to front-2-local — the
  registry maps them.)
- **Route → namespace declaration** via TanStack Router `staticData`:
  `createFileRoute(...)({ staticData: { i18nNamespaces: ['tenants'] } })`. The needed set for a
  navigation = globals ∪ (staticData namespaces of all matched routes).
- **SSR preload (no flash):** after route matching, compute the namespace union for the request
  locale, load them (inline dynamic import — module-cached), init the request i18next instance,
  render, dehydrate. Client hydrates with the same set → no flash.
- **Client on-demand:** on navigation, before rendering the target route's content, compute the
  union for the target matches and `await i18next.loadNamespaces(missing)` (backend fetches the
  Vite chunks); block in the route loader so there is no flash. Globals are always present.
- **Strict active-language-only (`fallbackLng: false`):** load only the active locale's namespaces
  — a French page loads only French chunks, never English. French completeness is enforced
  statically (`fr.ts satisfies LooseResource`) + by the namespace-aware key-coverage test, so
  nothing needs a runtime fallback. (Owner decision 2026-07-21, superseding an earlier
  load-en-fallback-for-fr idea.)
- **Client loading (captain correction to the spike):** client navigations load namespaces via the
  client-side Vite-glob backend (a lazy chunk `import()`), NOT a per-navigation server function —
  which would reintroduce the per-nav RPC stall #904/#905 just removed. The server function is
  SSR-only (runs inline).
- **Language switch:** set cookie → reload the currently-active namespaces in the new locale via
  `changeLanguage` (backend re-loads active ns) → re-render. No full reload.
- **Carries forward from the unblock PR:** client-local locale resolution (no per-nav serverFn) +
  stable context per locale.

## 5. Migration strategy (phased, incremental — one feature per PR)

- **P0 (in flight, separate PR):** de-RPC unblock + active-language + stable context. Kills the 20s.
- **P1 — infra + first namespace:** add the Vite-import backend + `staticData` namespace
  collection + SSR-preload/client-on-demand wiring, with the globals routed through the backend
  (no behavior change yet). Prove the whole path end-to-end by extracting ONE self-contained
  feature (recommend `auth`) out of `common` into its own namespace, declaring it on the auth
  routes, and verifying SSR-no-flash + on-demand load + fallback + language switch.
- **P2…Pn:** migrate remaining features out of `common` one namespace per PR: extract keys, update
  call sites (`useTranslation('ns')` / `t('key', { ns })`), declare `staticData`, update
  `i18n-key-coverage`. `common` shrinks each phase.
- Every phase: independent cross-family review + `just ci` (front-2 gates) + an SSR-no-flash e2e.

## 6. Testing

- Unit: namespace→chunk registry resolves every `(ns,lng)`; locale resolution; fallback loading.
- SSR no-flash (Playwright): visit a feature route with `fr` cookie → assert the feature's FR copy
  is in the initial SSR HTML (no EN flash).
- On-demand: navigating to a feature route triggers exactly that namespace's chunk; not before.
- Coverage: extend `i18n-key-coverage` for the per-namespace structure.
- Regression: zero per-nav serverFn; language switch reloads active namespaces.

## 7. Decisions (resolved — owner, 2026-07-21)

1. **Taxonomy** (§2) — approved.
2. **Source layout** (§3) — approved: `apps/front-2/src/i18n/locales/{lng}/{ns}.json`; `zod` +
   `response-message` stay in shared-ts.
3. **Backend** — hand-rolled `import.meta.glob` backend; no `i18next-resources-to-backend` dependency.
4. **Migration granularity** — one feature namespace per PR.
5. **Fallback** — strict `fallbackLng: false` (§4).
6. **Client loading** — client-side Vite-glob backend, no per-navigation server function (§4).
7. **Compile-time key safety** (resolved 2026-07-21, owner-approved) — P1 enforces cross-language
   **completeness** at compile time via `fr.ts satisfies LooseResource` (deep key-shape check;
   verifiably fails on a missing French key) plus the namespace-aware key-coverage test. It does
   **not** add an i18next `CustomTypeOptions` augmentation for call-site `t('key')` typo-catching:
   under the pinned TypeScript 6.0.2/6.0.3, an active large front-2 augmentation deterministically
   crashes the compiler (upstream bug — TypeScript issue #63195; confirmed by bisection + independent
   investigation; expression-level annotations only relocate the crash). front-2 has no active
   call-site key augmentation today (the shared-ts one is inert across the package/version boundary),
   so this is not a regression. Call-site typo-catching is a **step-by-step follow-up**: primary —
   adopt i18next's large-resource selector mode (i18next 25.4+, purpose-built for this) — #907; later —
   evaluate TypeScript 7 for front-2's typecheck (it does not crash) — #908. This is decoupled from the
   runtime loading design, which ships in full.

## 8. Framework spike — MUST lock before P1 build (de-risking)

TanStack Start has no `remix-i18next`; these mechanics are the implementation risk and get
confirmed in a short spike before the P1 plan is written:

1. TanStack Router `staticData` on file routes + reading matched routes' `staticData` at **both**
   SSR and client load time (likely `router.state.matches[].route.options.staticData`).
2. The exact hook point to **block render until namespaces load** that works for SSR + client +
   the error/notFound branches (must not violate shell-r5-F1 — i18n available to all shell branches).
3. i18next `loadNamespaces` + a Vite-import backend interplay under TanStack Start SSR
   (store dehydration/hydration), confirmed with a runtime smoke, not just types.
