## Findings

1. **Merge-blocker — §5.3 / C4: recurring occurrence identity is neither durable nor restart-aware.** [L1255](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1255), [L1266](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1266), [L1284](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1284), [L1746](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1746). The occurrence key lives only in `job_queue`; successful execution deletes it. A delayed duplicate firing after the first row completes therefore enqueues the same occurrence again, contradicting “exactly one row.” Separately, RAMJobStore cannot know which ticks were missed while no scheduler existed, so “fire-once-then-resume after a leader gap” contradicts §5.3’s own statement that restart misfires require persistent Quartz state. The catalog also lacks a startup assertion that every entry’s `JobDefinition` has a registered handler. **Fix:** add durable occurrence state with a unique `(job_key, scheduled_fire_at)` identity, written atomically with enqueue and retained beyond queue deletion. Reconciliation must derive missed occurrences from durable state and explicitly choose bounded catch-up or drop-on-gap semantics. Validate catalog→definition→handler closure at startup.

2. **Merge-blocker — §4.5/§5.4 / C1/F7: storing bytes does not define a transport that can resend those bytes.** [L776](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:776), [L785](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:785), [L1329](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1329), [L1380](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1380). `JobJson` serializes job payloads; it is not the Resend transport serializer. The existing abstraction still accepts semantic arguments and lets `ResendEmailAdapter`/the SDK construct and serialize the provider request. Nothing specified can feed `request_bytes` verbatim into that path, attach the job idempotency key, and prove those are the actual provider bytes. There is also a local race: two reclaimed handlers can both pass the step-0 `email_log` check before one waits on the SEND lock; the second does not recheck `email_log` after acquiring that lock and can call the provider again. **Fix:** specify an adapter boundary such as `SendPreparedAsync(ReadOnlyMemory<byte>, idempotencyKey)` that writes the persisted UTF-8 payload directly to the HTTP request, or weaken “exact bytes” to a provider-supported canonical request contract and prove it. Recheck `email_log(job_id)` inside the locked SEND transaction immediately before network I/O.

3. **Merge-blocker — §4.6/O6: legacy `Sent` rows are not evidence of provider acceptance.** [L68](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:68), [L741](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:741), [L863](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:863). The document correctly records F3: the old adapter returned `Success=false`, `EmailService` discarded it, and the dispatcher then marked the row `Sent`. O6 nevertheless maps every legacy `Sent` row to `Submitted`, whose declared meaning is “provider accepted.” That manufactures authoritative success history from rows known not to support that conclusion. **Fix:** migrate legacy `Sent` as an explicit `LegacySubmissionUnverified`/`Unknown` outcome, reconcile it against provider records if possible, or do not back-copy those rows. Never call them `Submitted` without evidence.

4. **Major — §5.1 / C7/F1: renewal retries consume the entire confirmed lease instead of preserving a safety margin.** [L1016](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1016), [L1025](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1025), [L1036](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1036). Cancelling only after a full lease window means the database lease may already have expired and another worker may already be executing. Restarting a local stopwatch after the renewal response is additionally later than the database stamp by the round-trip duration. Fencing protects settlement, not concurrent external side effects. The 633 tip implements this same unsafe edge, so this is not merely wording. **Fix:** have renewal return the database deadline/current database time, maintain an explicit safety margin covering expected DB latency, and abandon before—not at or after—`locked_until`. Test a transient outage spanning the safety deadline while another worker reclaims.

5. **Major — §4.6 / C2: zero rows proves data drain, not producer quiescence.** [L893](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:893), [L913](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:913), [L1882](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1882). `ACCESS EXCLUSIVE` plus zero `Pending`/`Processing` correctly prevents silent unsent-row loss. It does not prove that no old API binary remains capable of inserting afterward. Such a producer blocks behind the lock, then fails when the dropped table disappears, rolling back the invitation request. That is not data loss, but it is not a safe expand/contract gate either. **Fix:** make “all API producers are R1-or-newer and all old worker binaries are gone” an explicit, inspectable R2 precondition using immutable fleet tags/deployment state, then run the row-level lock/check. Add the blocked-old-producer case to the rollout analysis.

6. **Major — §3.2/§10 / C5/F17: the legacy-dispatcher role fix is assigned to the wrong parallel packet.** [L279](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:279), [L1814](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1814), [L1851](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1851), [L1893](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1893). Phase 2B claims `api` has zero worker services, but moving `InvitationEmailOutboxDispatcher` out of shared infrastructure is assigned to parallel Phase 2C-R1. Shipping 2B independently therefore violates D1; the current 634 tip demonstrates exactly that state. **Fix:** move the registration change into Phase 2B, with R1 merely retaining the already-worker-only dispatcher, or make 2C-R1 a hard prerequisite/atomic companion to 2B rather than parallel work.

7. **Major — §4.2 / C9/F16: DLQ requeue lacks both a usable definition registry and a single-use guard.** [L611](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:611), [L625](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:625), [L637](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:637), [L1086](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1086). `JobHandlerRegistry` maps types to handler factories; the document never defines a type-erased definition/validator that `RequeueDeadLetterAsync` can invoke for arbitrary stored JSON. Moreover, nothing rejects a second requeue of a DLQ row whose `requeued_as_job_id` is already set. Once the first new job completes and releases its idempotency key, the same DLQ row can create another job and overwrite its forward lineage. **Fix:** unify handler factory and payload validation in a `JobRegistration` registry, and condition requeue atomically on `requeued_as_job_id IS NULL`. Requeue a subsequent failure from its new DLQ row, never repeatedly from the ancestor.

8. **Major — §4.6/§5.1 / C11/F20: the claimed single sanitization boundary has two bypasses.** [L872](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:872), [L1176](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1176), [L1193](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1193). An `INSERT … SELECT` migration cannot pass values through a C# static `JobErrorSanitizer`; no executable migration mechanism is given. The live path then passes the unsanitized exception object—including its raw message—to Serilog. “Protected logs” are not redaction and can still persist recipient addresses, tokens, or provider bodies. **Fix:** either sanitize historical errors in SQL with an explicitly specified function or replace them with a stable migration code. Do not log raw provider/job exceptions containing untrusted messages; add a logging redaction/destructuring boundary or emit sanitized type/code plus safe stack metadata.

9. **Major — §5.1 / C14/F14: the registry escape hatch disables the guarantee it is supposed to preserve.** [L1091](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1091), [L1106](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1106). A global boolean permits the worker to start with any unsupported live queue type. The processor will then permanently dead-letter it. The stated use—“drain a retired version”—is impossible without that version’s handler; with the handler present, the escape hatch is unnecessary. **Fix:** never bypass unknown types in `job_queue`. If historical DLQ orphans must be tolerated, use an explicit audited allowlist limited to exact DLQ-only types, or deploy the old handler image to drain them.

10. **Major — §7/O8 / C12/F21: observability has contradictory release semantics and disappears with leadership.** [L1557](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1557), [L1563](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1563), [L1593](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1593), [L1606](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1606), [L1997](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1997). Phase 3 is simultaneously defined as telemetry-only and as wiring a real warning+ webhook route. More seriously, global sampling is leader-gated: when leadership is absent—the failure most needing detection—no replica samples queue state or emits threshold warnings. Silence becomes the symptom. **Fix:** state one release sequence, e.g. Phase 2A-R emits telemetry and Phase 3 wires the alert sink. Give monitoring an independent elected lease/heartbeat, or let every replica emit instance-tagged samples and aggregate them. Add an explicit `scheduler_leader_present`/sampling-staleness alert.

11. **Minor — §3.1/O7: prepared-send retention is claimed env-overridable but has no config variable.** [L228](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:228), [L1627](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1627), [L1990](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1990). Only email-log and DLQ retention variables are listed, while O7 says all three windows are environment variables. **Fix:** add `EMAIL_PREPARED_SEND_RETENTION_DAYS` with validation and Phase-3 wiring, or state that seven days is a fixed safety floor.

12. **Editorial — §4.5: `prepared_committed` represents no observable database state.** [L779](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:779), [L796](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:796). Other transactions cannot see an uncommitted insert, and every insert sets the flag true. The column can never validly distinguish the two lifecycle states. **Fix:** remove it; row existence means PREPARE committed. If an explicit timestamp is operationally useful, use `prepared_at`.

### C8 dispute ruling

**Accepted.** For this system, immediate intake stop plus immediate cancellation, conditioned proactive release, `CancellationToken.None` settlement of already-returned outcomes, and fencing for failed cleanup form a coherent shutdown model. At-least-once handlers already require idempotency, and external-effect handlers must have provider identity/reconciliation. Waiting for in-flight work would not strengthen correctness and would compete with the 30-second host timeout. The document no longer promises a grace period `BackgroundService` cannot provide.
