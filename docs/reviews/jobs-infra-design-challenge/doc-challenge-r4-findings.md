## Findings

1. **Major — R3-1/O10: reconciliation is neither monotonic nor schedule-revision-aware.** [§4.3 L792](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:792), [§5.3 L1598](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1598), [§5.3 L1624](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1624). `cutoff` is the latest expected fire under the current cron, yet the contract assigns `reconciled_through = cutoff`. For a sparse or edited cron, `cutoff` can precede the existing watermark. More importantly, changing cron/timezone or re-enabling a definition causes reconciliation to interpret the old interval using the new schedule; after ledger pruning, bounded catch-up can enqueue occurrences that were never scheduled or were intentionally disabled. The “never inspect at/below the durable bound” guarantee is therefore false across schedule revisions. **Fix:** update with `GREATEST(reconciled_through, cutoff)` and define revision semantics: store `schedule_revision/effective_from`, or atomically reset the watermark to database `now()` on cron/timezone/gap-policy changes and disabled→enabled transitions. Add sparse-cron, cron-edit, and disable-past-retention tests.

2. **Major — C4/R2-1: Quartz’s live misfire behavior can violate `DropOnGap`.** [§5.3 L1547](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1547), [§5.3 L1573](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1573), [§5.3 L1598](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1598), [§5.3 L1636](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1636). The catalog specifies timezone and a durable gap policy, but never specifies the actual CronTrigger misfire instruction. The current 634 branch uses plain `WithCronSchedule(cronExpression)`. Quartz’s default SmartPolicy for CronTrigger is `FireOnceNow`, so thread starvation or a paused live scheduler can enqueue a missed fire despite `DropOnGap`. This is separate from restart persistence. [Quartz documents that default explicitly.](https://www.quartz-scheduler.net/documentation/quartz-4.x/tutorial/crontriggers.html) **Fix:** require `WithMisfireHandlingInstructionDoNothing()` for dynamic triggers and make reconciliation the sole catch-up authority, or define an explicit per-entry Quartz policy consistent with the durable gap policy. Add a live-scheduler misfire test.

3. **Major — R3-2/O7/O11: prepared email bytes now survive for roughly the DLQ window, contradicting the stated seven-day sensitive-data policy.** [§3.1 L237](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:237), [§4.2 L704](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:704), [§4.5 L1012](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1012), [§4.5 L1016](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1016), [O7 L2485](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2485). The new requeue policy correctly retains prepared state while a DLQ row exists, but DLQ retention defaults to 90 days. Consequently, `request_body`—recipient, rendered body, and invitation/reset token—cannot be deleted by the seven-day anti-join sweep. Calling this a short-lived seven-day scratch is materially misleading. **Fix:** decide one coherent policy: encrypt prepared bodies and document the effective 90-day retention; cap email DLQ requeueability at seven days and mark older rows non-requeueable; or align email DLQ retention with prepared-send retention. Reflect the choice in dashboard behavior and access controls.

4. **Major — C6/F24: the claimed complete `APP_ROLE` entrypoint inventory omits the production migration runner.** [§3.1 L211](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:211), [Phase 2B L2283](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2283), [Phase 2B L2297](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2297). The Docker migrate target runs `dotnet ef database update` ([Dockerfile L35](/home/radan/Projects/PublyApp/publyapp/apps/api/Dockerfile:35)); the documented staging migrate service sets `Production` but omits `APP_ROLE` ([staging-deploy.md L73](/home/radan/Projects/PublyApp/publyapp/docs/front-2-migration/staging-deploy.md:73)). There is no design-time context factory, and model creation reads `AppEnvironment`, so implementing the proposed production fail-fast makes this migration path fail before applying migrations. **Fix:** add every production/staging migrate job and production-like host invocation to the enumerated entrypoints, pin `APP_ROLE=api`, update the staging/Dokploy shape, and include the migrate target in Phase 2B’s gate.

5. **Major — R3-6: the alert lease prevents concurrent sends, not duplicate notifications after an ambiguous response.** [§7.2 L2020](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2020), [§7.2 L2037](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2037), [Phase 3 L2405](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2405). If the webhook accepts and the worker crashes before setting `notification_sent_at`, another replica retries after 60 seconds. The document delegates correctness to a “configured receiver” honoring the supplied idempotency key, but O8 names only a generic Serilog webhook sink and existing notification channel—no receiver contract proves such deduplication. The gate’s “exactly one rendered notification” is therefore absorption by assumption. **Fix:** either state at-least-once notification delivery honestly, or select and specify a receiver that guarantees idempotency for that header/key, including retention and response semantics, then test accept-without-response → lease expiry → retry against that receiver contract.

6. **Minor — prepared-send cleanup names a nonexistent DLQ column.** [§4.2 L595](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:595), [§4.5 L1016](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1016), [§7.3 L2055](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2055), [§9 L2203](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2203). `job_dead_letter` has `original_job_id`, not `job_id`, but the anti-join is repeatedly described as testing whether the prepared row’s `job_id` exists “in `job_dead_letter`.” **Fix:** specify the exact predicate `job_dead_letter.original_job_id = email_prepared_sends.job_id` and test first DLQ, requeue transfer, and re-dead-letter lineage.

7. **Minor — the rollout overstates when #811 becomes guaranteed.** [§1 L66](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:66), [§4.6 L1099](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1099), [§5.4 L1701](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1701). R1 explicitly lets the legacy dispatcher drain under “old semantics.” Remaining Processing rows—and Pending rows inserted by a pre-R1 producer during rollout—therefore retain the old eligibility-check/send race until R2 quiescence. **Fix:** state that the #811 guarantee begins only after R2, or harden the R1 drainer with the domain-row-lock linearization and document the irreducible already-in-flight cutover window.
