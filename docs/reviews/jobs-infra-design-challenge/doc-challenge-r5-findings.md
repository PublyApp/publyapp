# PR #852 jobs/worker design challenge — Round 5

Round 5 resolves five of the seven Round-4 findings completely, but two remediations remain incomplete at mechanism level. There are no merge-blockers; the two majors still make the document unsafe as the authoritative implementation reference.

## Findings

1. **Major — R4-1/O15: schedule revisions reset durable history but do not fence the superseded live Quartz trigger, and the two occurrence paths have an unsafe lock order.** [§4.3 L831](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:831), [§4.3 L865](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:865), [§5.3 L1661](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1661), [§5.3 L1684](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1684), [§9 L2302](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2302). `schedule_policy_fingerprint` is stored on the definition, but `SyncSystemJobsJob` puts only `job_key` in `JobDataMap`. After a dashboard cron edit commits its reset, the old RAM-store trigger can fire during the documented ~60-second reconciliation interval; `EnqueueSystemJobJob` has no revision token to reject it, so it can persist a unique occurrence from the superseded schedule after the new policy's effective boundary. The occurrence PK does not help because the old fire time is unique. There is also a lock-order inversion: reconciliation locks the definition then inserts occurrences, while normal delivery inserts the occurrence and only later stamps `last_enqueued_at`; a same-tick collision can deadlock on the occurrence PK versus the definition row. **Fix:** stamp the current schedule fingerprint/revision into every trigger. In `EnqueueSystemJobJob`, begin the transaction by locking the definition row, then require enabled/non-deleted state and an exact trigger-fingerprint match before inserting the occurrence. Make reconciliation take the same definition-first lock order. Add (a) edit-commit → forced old-trigger-fire → no ledger/job and (b) concurrent live-fire/reconciliation → no deadlock/loss specs.

2. **Major — R4-3/O16: expiry deletes the only durable evidence needed to render or return `PreparedStateExpired`.** [§4.2 L621](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:621), [§4.2 L695](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:695), [§4.5 L1007](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1007), [§5.4 L1861](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1861), [§7.3 L2165](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2165), [§10 L2554](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2554). The seven-day cutoff is anchored to `email_prepared_sends.prepared_at`, but the sweep deletes that row and `job_dead_letter` stores neither `prepared_at`/expiry nor an expiry status. “Reports the affected DLQ ids” is not durable state a later dashboard request can query. After deletion, `RequeueDeadLetterAsync` can observe only “missing”; it cannot distinguish an expected expiry from premature loss/corruption, and `failed_at` is not a valid substitute because preparation can precede dead-lettering by hours or an outage. The current send-flow sentence at L1864 also directly contradicts the remediation by saying cleanup waits until DLQ lineage is gone. **Fix:** persist prepared-state metadata on the DLQ (for example `external_state_prepared_at`, `external_state_expires_at`, and status/expired-at). Have the sweep atomically delete the bytes, stamp the matching DLQ row expired, and audit the transition; requeue and dashboard read that durable state and distinguish `Expired` from `Missing`. Correct L1864 and add a post-sweep, fresh-context/dashboard-query regression.

3. **Minor — the new alert-delivery table claims retention without defining a window, sweep, or supporting index.** [§7.2 L2120](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2120), [§7.2 L2153](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2153), [§7.3 L2163](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2163), [Phase 3 L2532](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2532). `job_alert_delivery_leases` creates one row per breached condition per five-minute window, then says rows older than “the alert audit window” are pruned. No duration/config exists, §7.3 omits its retention job, Phase 3 omits it from the sweep inventory, and the PK `(condition_key, window_started_at)` does not support an efficient global age sweep. **Fix:** define the retention default/config, add an index beginning with `window_started_at`, and name the batched sweep in §7.3 and Phase 3.
