# PR #852 jobs/worker design challenge — Round 7

Round 7 genuinely closes the schedule-epoch, prospective-expiry, and lock-order defects. O18's reversal is correct. O20/O21 are also the right decisions, but the new external-state design still omits one build-grade dispatch seam, and the PREPARE marker write is not safe under the lease-loss/concurrent-PREPARE race the engine explicitly supports. There are no merge-blockers; two majors still make the document unsafe as the authoritative Phase 2A/2C implementation reference.

## Findings

1. **Major — R6-4/O20: the engine is told to classify email-specific prepared state at dead-letter time, but no type-erased dead-letter-classification capability exists.** §4.2 [L719](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:719), [L742](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:742), [L759](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:759); §5.1 [L1827](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1827), [L1935](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1935); §5.4 [L2328](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2328); §10 [L2957](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2957). `JobDeadLetter.FromJob` must distinguish `Present` from `Missing` by checking `email_prepared_sends`, yet the unified `JobRegistration` exposes only a handler factory, payload validator, and **requeue** transfer hook. `OnTerminalFailureAsync` returns only `Task` and, by the documented order, runs before the engine creates/inserts the DLQ row; it has no stated way to return or stamp the classification. A generic entity factory also cannot query an email-specific table without coupling the engine to email, and future webhook/publishing prepared-state stores make that coupling untenable. The prose therefore asserts a total state machine without specifying who computes its non-generic state. **Fix:** add a type-erased terminal external-state hook to `JobRegistration`, e.g. `ClassifyExternalStateAsync(JobQueueItem, JobDeadLetter, AppDbContext, ct)`, required alongside `TransferExternalEffectState`; create the DLQ entity first, invoke the hook inside the terminal transaction, then run the handler terminal hook, insert DLQ, and fenced-delete the queue row. `Standard` sets `None`; invalid-before-handler with a NULL marker sets `NeverPrepared` without resolving a handler; email's hook performs marker-first/scratch-second classification. Add the capability to the exact registration-set/startup-gate specs.

2. **Major — R6-4/O20: PREPARE's marker write is neither fencing-conditioned nor tied to the row actually inserted, so the claimed equality/commit proof fails under concurrent reclaimed handlers.** §4.5 [L1364](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1364), [L1366](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1366); §5.4 [L2275](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2275); §6 [L2461](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2461). The contract says `INSERT ... ON CONFLICT DO NOTHING` and independently sets `job_queue.external_prepared_at = now()`, then claims that marker and `email_prepared_sends.prepared_at` are equal “by construction.” Two workers can both observe no scratch before serializing on the domain lock; the loser can hit `DO NOTHING` against the winner's row and still overwrite the marker with a later `now()`. More seriously, a token-ignoring stale owner can reach PREPARE after lease loss, insert an orphan scratch or mutate the currently owned queue row unless the queue update is fenced and its row count controls the transaction. That violates §6's “every transition is conditioned on the token,” can extend the advertised sensitive-byte cutoff beyond the actual `prepared_at`, and can commit scratch after the queue row was already settled. **Fix:** make PREPARE one fenced transaction: lock/recheck the prepared row after acquiring the domain lock; insert once and obtain its database `prepared_at` (or read the conflict winner's value); set `external_prepared_at` to that exact value only when NULL/equal via `WHERE id = ... AND lock_token = ...`; require one affected queue row or roll the entire transaction back. Add a barrier spec with an expired/reclaimed owner and current owner proving one immutable scratch, marker equality, stale-owner rollback, and no orphan after settlement.

3. **Minor — R6-4/O20/O21: three current-contract summaries still contradict the detailed state machine.** §4.2 [L669](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:669), [L821](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:821), [L861](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:861); §6 [L2483](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2483). The DDL comment says `external_state_prepared_at` is copied from the scratch row, but `Missing` has no scratch and the detailed rule correctly copies the marker. The requeue gate says `requeued_as_job_id IS NOT NULL` is “always `5 Transferred`,” while the self-reported CHECK fix correctly keeps a requeued `NeverPrepared` ancestor at status 3. The failure-semantics summary says every poison job invokes `OnTerminalFailureAsync`, directly contradicting O21's no-hook invalid-before-handler settlement. **Fix:** source the timestamp comment from `job_queue.external_prepared_at`; make the gate say “already requeued regardless of external-state status (`Transferred` only when state moved)”; qualify §6's hook with “handler-reached terminal paths,” and state DLQ-only settlement for invalid-before-handler failures.

## Decision rulings

- **O18 accepted.** The reversal is technically correct: policy equality cannot fence registration epochs. UUID epochs close A→B→A, disable→enable, and delete/recreate without relying on a per-row counter that can restart. Trigger replacement plus exact epoch matching is sufficient; no additional monotonic counter is needed.
- **O20 accepted in direction, incomplete in integration.** A non-sensitive timestamp outside deletable scratch is the correct way to distinguish pre-PREPARE failure from premature scratch loss. It carries no recipient, body, token, hash, provider key, or other material that reopens O16's privacy decision. Findings 1–2 concern the terminal-classification seam and race-safe write, not the marker choice.
- **O21 accepted.** Invalid-before-handler work has no recipient-bearing handler context, so DLQ-only `NeverPrepared` settlement is more honest than inventing a recipient or weakening `email_log.recipient`. The §6 contradiction is stale summary text, not a reason to reject the decision.
- **Self-reported defect (a) closed.** Requeue now branches on prepared-row existence before time, so vanished bytes become `Missing`, never policy expiry.
- **Self-reported defect (b) closed in the detailed mechanism but not the summary table.** The transfer hook correctly leaves a `NeverPrepared` ancestor at status 3 and relies on `requeued_as_job_id` for single use; remove the false “always Transferred” parenthetical.
- **R5-3 scope call remains correct.** The three extra age-leading indexes are necessary for the sweeps they already document and are not scope creep.

## Attacked and held

- **Epoch fence:** rapid A→B→A before sync, disable→enable, delete/recreate, current-epoch duplicate triggers, and a delayed old execution were attacked. Exact epoch matching rejects only retired registrations; the occurrence PK still deduplicates same-tick current fires.
- **Fingerprint input set:** cron, timezone, and gap policy are the fields that require trigger-policy replacement. Handler/job-type/payload-factory changes resolve through the live catalog at fire time and do not need to be trigger identity inputs.
- **Definition/occurrence lock order:** both live delivery and reconciliation take the definition first. No opposite acquisition remains in the documented occurrence paths.
- **Prospective expiry:** requeue cannot transfer at/after its stored cutoff even before the sweep runs; config changes cannot move an existing DLQ boundary; expired-and-vanished remains `Missing`, not `Expired`.
- **Sweep/requeue concurrency:** both serialize on the DLQ before touching scratch. `SKIP LOCKED` is used only for throughput, and the delete→stamp dependency prevents an `Expired` status without deletion by that statement.
- **Six-value meanings:** with the corrections above, `None`, `Present`, `Expired`, `NeverPrepared`, `Missing`, and `Transferred` are distinct; `requeued_as_job_id`, not status 5, is the universal single-use fact.
- **Fold reality:** `origin/feat/809-email-jobs-fold` really writes `status = 4` plus `last_error = 'folded to job_queue'`, and the shipped dispatcher claims only Pending or stale Processing, so the sentinel is unclaimable. The branch's remaining migration/code gaps are disclosed alignment items.
- **Code-alignment honesty:** 634 still has no epoch and uses default `WithCronSchedule`; 633 lacks the marker/state columns; 809 still invokes the existing terminal hook path. The document flags these as code-lag/live-defect items rather than misdescribing current code.
- **Cross-reference pass:** all live §3–§11 targets exist; review-record paths through round 6 exist; no active two-lane, in-process signal, global registry bypass, leader-gated sampler, or fingerprint-as-fence contract survives outside explicitly historical/superseded text.
- **C8 remains accepted:** immediate cancellation, `CancellationToken.None` settlement/release, fencing, and idempotent replay remain coherent for this system.
- Static-only review: no checkout, build, tests, containers, Testcontainers, or database access was used. The only write was this requested findings artifact.
