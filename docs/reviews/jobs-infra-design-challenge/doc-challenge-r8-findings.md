# PR #852 jobs/worker design challenge — Round 8

Round 8 genuinely adds the missing classification dispatch seam and makes the PREPARE SQL fence-safe. O22 and O23 are sound decisions. The document is still not merge-ready as an implementation-authoritative reference because three build-grade defects remain inside the new mechanisms: the classifier is not payload-blind by signature, the required PREPARE concurrency gate describes an impossible lock interleaving and a false control result, and the new engine-owned marker operation is neither policy-enforced nor assigned to the phase that owns engine contracts. There are no merge-blockers.

## Findings

1. **Major — R7-1/O22: `ClassifyExternalStateAsync` is not payload-blind by signature, and the live contract does not cover the fallback branch its ratification record claims.** §4.2 [L718](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:718), [L760](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:760); §5.1 [L1966](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1966), [L1979](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1979), [L1992](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1992), [L2119](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:2119); Ratification record [L4223](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:4223). The API receives the complete `JobQueueItem` and `JobDeadLetter`; both expose the malformed payload the text says is “not reachable from the classifier's signature.” It also receives a writable `AppDbContext`, so the “only permitted write” is convention, not an API boundary. The startup gate proves only that a delegate exists; it cannot prevent that delegate from parsing payload, mutating envelope fields, no-oping to the CHECK-valid default `0 None`, or deterministically throwing. Because every classifier failure rolls the terminal transaction back, any such deterministic defect recreates the infinite re-lease loop O21 was meant to close. The current status table also specifies unregistered → `NeverPrepared` only for a NULL marker, while the chronological record claims marker-set/no-classifier → audited `Missing`; no live section implements that conservative branch. **Fix:** replace the mutable-entity signature with a restricted input and returned value, e.g. `ExternalStateClassificationInput(JobId, JobType, ExternalPreparedAt)` → `ExternalStateClassification`, with no payload-bearing object and no mutable DLQ entity. Have the engine apply and validate the returned fields. Engine-classify marker-NULL invalid-before-handler work without invoking a custom classifier; explicitly define marker-set/no-registration (and marker-set/`Standard`) as a conservative integrity failure. Add a deterministic-throw/no-op classifier control proving the engine cannot silently emit `None` or loop malformed input forever.

2. **Major — R7-2/O23: the mandatory reclaimed-owner PREPARE spec cannot execute in the stated order, and its second control cannot produce the claimed orphan.** §4.5 [L1384](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1384), [L1435](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1435); §9 [L3108](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3108); Phase 2C-R1 gate [L3327](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3327). Owner A is paused *inside* its transaction after `SELECT … FOR UPDATE` on the domain row. That row lock remains held until A commits or rolls back, so owner B can reclaim `job_queue` but cannot “PREPARE to completion” before A is released; B blocks on the same domain lock. The asserted barrier schedule is therefore unconstructible. Dropping only `AND lock_token = {token}` also does not “produce the orphan”: while the queue row exists it lets stale A commit A's scratch/marker and B later adopts those bytes; after settlement `WHERE id = {jobId}` still matches zero rows, so the rowcount rollback still prevents an orphan. **Fix:** specify the real schedule: A locks domain and pauses before marker; B reclaims and is proved blocked on domain; release A; A's fenced marker affects zero and rolls its transaction back; B then acquires domain and commits its own scratch/marker. Make the no-token control assert stale A's bytes/marker wrongly commit under B's ownership. Use a separate post-settlement control that removes the rowcount-or-rollback rule—not merely the token predicate—to demonstrate orphan scratch. Keep the independent-`now()` mismatch control.

3. **Major — R7-2/O23: the claimed two-writer marker invariant is not enforced, and the packet map never assigns `StampExternalPreparedAsync` to 2A-R.** §4.5 [L1397](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1397), [L1420](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1420); §5.1 [L1998](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1998); Phase 2A-R [L3143](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3143), Phase 2C-R1 [L3292](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3292), phase-ownership rule [L3365](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3365), [L3390](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3390). The method signature accepts only ids, timestamp, context, and token; it has no registration/policy proof and no stated active-transaction guard. Any same-assembly handler can call it, including a `Standard` registration, so “both writers are reachable only for a `TransferExternalEffectState` type” is assertion-by-call-site. F15's architecture guard catches direct `job_queue` writes outside `Infrastructure/Jobs`, not calls into this unrestricted engine method. Separately, §10 adds the marker column in 2A-R and tells 2C to use the fenced transaction, but never creates or touches a file for `StampExternalPreparedAsync`; §10 simultaneously says 2A-R owns engine contracts and 2C only consumes them. An implementer following the packets must either leave the operation missing or violate the phase boundary. **Fix:** assign a named interface/implementation and its specs to Phase 2A-R. Make the engine operation verify the locked queue row's `job_type` resolves to `TransferExternalEffectState`, require an active caller transaction, and fail before writing otherwise; add an architecture/runtime spec proving a `Standard` handler cannot stamp the marker. Phase 2C should only call the pre-existing seam.

4. **Minor — two current-contract summaries still describe the superseded independent-`now()` marker write.** §4.2 [L751](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:751); O20 [L3665](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3665). Both say the marker is written from the “same database `now()`” as `prepared_at`. O23's actual mechanism reads the scratch row's returned `prepared_at` (or the conflict winner's value) and writes that exact value; there is no second marker-side `now()`. The equality conclusion survives, but the stated mechanism is exactly the one R7-2 replaced. **Fix:** say the marker takes the committed scratch row's own `prepared_at`, returned/read inside the fenced transaction; annotate O20 as completed/superseded at write level by O23.

5. **Editorial — §8's placement summary omits the fourth registration capability.** §8 [L3004](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3004). The “unified `JobRegistration`” parenthetical lists factory/validator/requeue policy but omits O22's classifier, despite §5.1 and §10 calling it the fourth capability. **Fix:** add the terminal external-state classifier to the summary and qualify “the engine never reads or writes” the messaging tables as “the generic engine has no direct table coupling; registered type-specific delegates do.”

## Attacked and held

- **PREPARE data race:** the actual transaction survives concurrent absent-row checks, unique-index conflict waiting, stale-owner lease loss, an already-set equal marker, and settlement-before-stamp. `ON CONFLICT DO NOTHING` plus winner re-read is sufficient when followed by the token/rowcount rollback.
- **Marker equality:** using the persisted row's own `prepared_at` makes equality real, including the conflict-loser and transferred-row paths; no second timestamp is needed.
- **Classifier location:** placing type-specific store knowledge in a registration delegate avoids welding generic engine code to `email_prepared_sends` and scales to webhook/publishing stores.
- **Capability pairing:** for registered types, `TransferExternalEffectState` ⇒ both classifier and transfer hook, while `Standard` ⇒ neither custom capability, is a complete presence check and correctly fails composition on drift.
- **Terminal order:** create → classify → handler hook when reached → insert → fenced delete is coherent and keeps the DLQ entity available for classification while preserving F5 atomicity.
- **R7-3 repairs:** all three named stale summaries were corrected at their source without weakening the detailed rules.
- **Code-alignment honesty:** static branch inspection confirms 633 still has the older registry/terminal shape and no marker/classifier, 634 still uses the default cron schedule and no epoch, and 809 still uses the pre-O22/O23 email shape. The document labels these as lagging code rather than current implementation. The 809 hook currently catches malformed JSON with an `(unknown)` placeholder, so the exact loop is not proven by that branch alone; the document calls it *suspected* and requires direct captain verification, while O21 explicitly replaces that placeholder strategy. That is acceptable flagging, not a new defect.
- **Cross-reference integrity:** every live §1–§11 target exists; all round-1–round-7 committed review paths exist; no active two-lane, in-process-signal, fingerprint-fence, global registry bypass, or leader-gated sampler contract survives outside annotated historical text.
- **Settled ground:** C8 immediate cancellation/release semantics and every previously held R1–R6 mechanism were not re-litigated.
- Static-only review: no checkout, build, tests, containers, Testcontainers, or database access was used. The only write was this requested findings artifact.
