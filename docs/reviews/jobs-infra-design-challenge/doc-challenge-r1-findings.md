# PR #852 merge-challenge round 1 findings (sol@high, 2026-07-17)

1. **Merge-blocker — §4.5/§5.4, [L601–626](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:601), [L975–1005](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:975): the prepared-envelope guarantee is not implementable as specified.** The handler opens one transaction, locks the domain row, inserts the scratch row, calls the provider, then commits. If the provider accepts and the process crashes before commit, both `email_prepared_sends` and `email_log` roll back; the retry re-renders mutable state, defeating F7. Additionally, `jsonb` does not preserve “persisted bytes,” and the document never says a transient failure commits the scratch row. The seven-day sweep can also delete a live job’s envelope because “orphan” is undefined. **Fix:** specify a committed prepare transaction followed by a second locked eligibility/send transaction; persist canonical request bytes as `text`/`bytea` or define deterministic canonical serialization; commit the scratch on transient failure; and make cleanup anti-join live `job_queue`/DLQ state—age alone must never delete it.

2. **Merge-blocker — §4.6, [L682–690](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:682): R2 can drop unsent work.** The migration aborts only for non-terminal rows “younger than the lease window.” A stale `Processing` row older than five minutes is precisely a row the R1 dispatcher must reclaim; this predicate instead permits dropping it. **Fix:** acquire an exclusive table lock, then require zero `Pending` and zero `Processing` rows regardless of age before back-copy/drop. Test both fresh and stale `Processing` rows plus fresh rows inserted by an old producer during the R1 rollout.

3. **Merge-blocker — §4.6/O6, [L652–689](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:652): the R1/R2 back-copy manufactures false cancellation history.** R1 back-copies terminal rows first, then marks every folded `Pending` source row `Cancelled` with `last_error='folded to job_queue'`. R2 subsequently back-copies terminal rows created during R1, mapping those bridge markers to `CancelledIneligible`. Each folded email can therefore acquire a false cancellation record plus its real new-job outcome. **Fix:** represent “folded” separately or explicitly exclude the bridge marker from historical back-copy; copy only genuine delivery outcomes; add a unique index on `legacy_outbox_id`; define legacy timestamp mapping; and sanitize or discard historical raw errors.

4. **Merge-blocker — §4.3/§5.1/§5.3/Phase 3, [L512–536](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:512), [L785–825](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:785), [L901–919](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:901): recurring-system-job dispatch has no coherent contract.** `job_key` is described as a stable value such as `session-cleanup`, while every queue `job_type` must be versioned. The schema has no payload or definition mapping, and the document omits the dispatching Quartz job entirely. Reality confirms the hole: `origin/feat/634-app-role-quartz` had to invent `EnqueueSystemJobJob`, which directly constructs `JobQueueItem`, bypassing F15. **Fix:** define a `SystemJobCatalog` mapping stable `job_key` to a versioned `JobDefinition`, payload factory, cron timezone/misfire policy, and scheduled-occurrence idempotency key; require Quartz to enqueue exclusively through `IJobEnqueuer`; reject/disable catalog-unknown rows; name the seeder, dispatcher, registration, and adversarial specs.

5. **Major — D1/§3.2/§4.6/Phase 2B, [L99–109](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:99), [L228–252](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:228), [L675–691](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:675): role composition ignores the legacy outbox during R1.** D1 says API registers no job hosted services, yet R1 says the old dispatcher ships unchanged. The 2B branch registers that dispatcher in shared `AddInfraServices`, so both API and worker run it, while the composition test only guards `Infrastructure.Jobs`. **Fix:** move the legacy dispatcher into worker-only registration during 2B/R1, or document a bounded transitional exception. The composition spec must inspect every `IHostedService`, not only one namespace.

6. **Major — §3.1/§3.3/F24, [L173–189](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:173), [L254–262](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:254): `All` remains an unsafe global fallback.** The document simultaneously reserves `All` for development and defaults to it in every environment. It pins only Docker publish and front-2 E2E; the real OpenAPI drift workflow and `just build-api` execute the application without `APP_ROLE`, constructing the worker surface. **Fix:** default to `All` only in Development/Testing and fail fast when Production lacks `APP_ROLE`; enumerate and pin all CI/OpenAPI/build entrypoints.

7. **Major — §5.1/F1, [L745–774](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:745): renewal failure semantics are wrong.** Zero affected rows proves lost ownership; a connection exception does not. Immediate cancellation on any renewal failure creates needless retries, while waiting until the next `lease/2` tick can overrun the original lease. **Fix:** track the last confirmed database lease deadline, retry transient renewal errors with short bounded backoff inside a safety margin, and abandon only on confirmed zero rows or when no safe renewal margin remains.

8. **Major — §3.6/§5.1, [L330–347](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:330), [L838–845](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:838): graceful drain contradicts `BackgroundService` cancellation.** The host cancels `stoppingToken` immediately, but the document says handlers continue until the 30-second budget nears exhaustion. Those semantics require different tokens. **Fix:** specify an intake-stop token and a separate force-cancel deadline, normally via an overridden `StopAsync`; stop claims immediately, wait for in-flight work, then cancel/release only at the deadline.

9. **Major — §4.2/F16, [L464–507](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:464): DLQ requeue cannot be implemented through the shown enqueuer.** `IJobEnqueuer` accepts typed payload plus an idempotency key; it cannot restore stored priority, max attempts, tenant, actor, correlation, or lineage. Re-dead-lettering also loses the chain to the prior DLQ row. **Fix:** define a privileged engine-only `RequeueDeadLetterAsync` that validates stored payload through the registered definition, restores the approved envelope, records `requeued_from_dead_letter_id`/new job linkage, and writes the audit record atomically.

10. **Major — §4.1/F13/Epic D, [L451–462](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:451), [L1453–1455](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1453): a domain marker does not make external publishing idempotent.** `scheduled_posts.published_at` cannot be committed atomically with a provider API call; a crash after provider acceptance but before the marker commits can publish twice. **Fix:** require every external-side-effect job to define a stable provider idempotency identity or reconciliation protocol plus an immutable prepared request and persisted receipt. For Bluesky, the later D3 design must use a deterministic record key or equivalent conflict reconciliation.

11. **Major — §4/§5.1/F20, [L383–405](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:383), [L847–864](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:847): sanitization is absorption-by-assertion.** The document repeatedly says errors are sanitized but defines only truncation. Arbitrary `Exception.Message`, `Retry.Error`, and `PermanentFailure(reason)` can contain addresses, tokens, payload fragments, or provider bodies. **Fix:** define structured safe error codes and a centralized persistence sanitizer that never stores raw exception messages; preserve detailed exceptions only in appropriately protected logs after redaction.

12. **Major — §7/F21, [L1137–1179](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1137): observability v1 does not actually alert.** The existing stack has console/file Serilog sinks, not a log-alert route; warning logs are telemetry, not alerts. `Meter` instruments have no exporter. The design also lacks scheduler-leader/sync/trigger health and listener-connected/last-catch-up signals, while “any replica” makes every worker emit duplicate global gauges and warnings. **Fix:** either wire and name a real alert destination in Phase 3 or state honestly that v1 is telemetry-only; leader-gate global sampling and add scheduler/listener health plus last successful execution timestamps.

13. **Major — status/Phase 3/Phase 4/O6/O7, [L3–8](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:3), [L1426–1445](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1426), [L1466–1497](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1466): it is not yet the claimed self-contained build spec.** Phase 3 lacks concrete job types, payloads, cron defaults/timezone, batch SQL, seeder ownership, and exact idempotency markers. Phase 4 explicitly says “sketch only,” contradicting the opening promise that every phase can be implemented without re-derivation. O6 and O7 remain unratified while their recommendations are already embedded in schema and build packets. **Fix:** ratify O6/O7 and add complete Phase 3/4 contracts, or narrow the document’s authoritative claim to Phases 2A–2C and require separate Phase 3/4 specs.

14. **Major — §5.1/F14, [L812–825](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:812): payload-version compatibility is advisory, not enforced.** A startup warning checks only DLQ types and fires after damage; it does not prevent a new worker from consuming a queued old type and permanently dead-lettering it. **Fix:** make worker startup/deploy fail closed when queued or DLQ types lack registered compatibility, query both tables, and define a release gate proving old API producers are gone before handler removal.

15. **Minor — §5.1/§5.4, [L796–800](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:796): per-definition leases are promised but absent from the schema and interface.** `JobDefinition` supposedly owns a lease and email handlers may differ by lease, yet `job_queue` has no lease-duration column and claiming uses one global setting. **Fix:** either remove the per-definition lease claim or add it consistently to definition, queue/DLQ envelope, claim, renewal, and requeue.

16. **Minor — §5.1/F9, [L723–743](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:723): the SQL shown does not preserve claim order.** PostgreSQL does not guarantee `UPDATE … RETURNING` order. The 633 branch correctly re-queries and sorts, but the authoritative document omits that mechanism. **Fix:** explicitly require the post-claim ordered query or return/order sufficient fields before dispatch.

17. **Minor — §5.5, [L1061–1079](/home/radan/Projects/PublyApp/jobs-design/docs/implementation-plans/jobs-worker-infrastructure.md:1061): the listener topology and herd analysis are imprecise.** There is one listener per worker replica, not one fleet-wide listener, and PostgreSQL broadcasts each notification to every listening session. Local signal coalescing does not eliminate the cross-replica claim herd. **Fix:** state the per-replica topology, accept the bounded no-op claims explicitly, and specify reconnect backoff/jitter and non-pooled or continuously held connection behavior.
